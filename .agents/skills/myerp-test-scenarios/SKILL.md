# MyERP 測試情境設計

依據 MASTER_PROMPT 第 20.2 節。目標：每個功能在寫代碼前就列出全部情境，邊界與錯誤情況不被遺漏。

## 步驟

1. 讀該功能的 requirements.md 與 business-rules.md，找出所有規則。
2. 按下表逐類列出情境；每一類都要寫，不適用的寫「不適用：理由」。
3. 每個情境指定測試層級：單元（U）、整合（I，真實 SQL）、E2E（E）。
4. 寫入 `docs/02-modules/<模組>/test-plan.md`，每個情境一個 ID（例如 `MD-SUP-IMP-007`），與需求 ID 對應。
5. 先寫失敗的測試，再實作。

## 情境類別

| 類別 | 必問的問題 |
|---|---|
| 正常 | 典型成功路徑是甚麼？ |
| 邊界 | 空值、最大長度、最大筆數、小數位上限、日期邊界（月底、跨年、閏年）？ |
| 重複與衝突 | 代碼已存在？代碼屬於**已軟刪除**的記錄？兩人同時修改（409）？ |
| 部分結果 | 批次中部分成功？**全部略過**？全部失敗？0 筆？ |
| 權限 | 無權限？跨公司？資料範圍外？ |
| 狀態 | 草稿 / 審批中 / 已核准 / 已過帳 / 已作廢時，哪些操作被禁止？ |
| 關聯 | 被其他資料引用時可否刪除或停用？引用的資料已停用時？ |
| 錯誤 | 後端 400 / 409 / 422 / 500 / 逾時，前端顯示甚麼？ |
| 檔案（如有） | 空檔、格式錯、超過大小 / 列數、編碼錯、欄位缺失、多餘欄位？ |

## 每個 E2E 情境的斷言

E2E 必須同時斷言兩件事，缺一不可：

1. **畫面**：顯示的訊息、樣式（成功 / 警告 / 錯誤）、筆數、原因。
2. **資料**：經 API 或列表確認實際的變更與訊息一致。

例：匯入 3 列，其中 1 列代碼已存在 →
- 畫面：警告樣式、「新增 2、略過 1」、該列顯示「代碼已存在」
- 資料：列表實際多了 2 筆，既有那筆內容沒有被改動

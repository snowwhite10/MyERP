# SYS 組織業務規則

1. 公司是資料隔離根。不得將客戶端提供的 `X-Company-Id` 視為授權；正式查詢前必須查核用戶公司權限。
2. 公司代碼全域唯一；分店／部門代碼在公司內唯一。軟刪除後不可重用代碼。
   代碼輸入先去除首尾空白並轉大寫，只允許 1–30 個 ASCII 英文字母、數字、連字號或底線；名稱去除首尾空白後須為 1–200 字元。
3. 部門所屬分店及上級部門必須與該部門同公司；上級鏈不可形成循環。
4. 已有業務資料引用的組織主檔只能停用。停用不改歷史資料；新業務單據不得選取停用組織。
5. 組織修改使用樂觀鎖 `version`；審計欄位由共用 interceptor 填入。
6. 停用部門後不可作為新部門的上級；停用公司後，內部服務不得在該公司建立新分店或部門。

## 用戶及密碼

7. 帳號去除首尾空白，限 3–100 個 ASCII 字母、數字、點、底線及連字號；以大寫正規化值判斷全系統唯一，刪除後也不可重用。
8. 密碼使用 ASP.NET Core Identity `PasswordHasher<SystemUser>`；預設至少 12 字元，須有大小寫、數字與符號，90 天到期。`Security:PasswordPolicy` 可調整長度、複雜度與到期天數；到期天數 0 表示停用到期檢查。
9. 連續錯誤 5 次鎖定 15 分鐘，鎖定期間不驗證密碼；到期後重設失敗次數。成功後清除失敗次數及鎖定期限。登入流程簽發 Token 前須檢查密碼到期。
10. 密碼、雜湊及 Token 不得寫入日誌或 API 回應；後續管理 API 須在 WU-SYS-004 授權後接入。

## 登入與 Token

11. 登入順序：欄位驗證 → Captcha（一次性，錯誤亦作廢）→ 以正規化帳號查用戶 → `VerifyPasswordAsync`（鎖定與失敗計數）→ 密碼到期檢查 → 簽發 Token。帳號不存在時仍做一次雜湊驗證，使回應時間接近。
12. Access Token 15 分鐘，無狀態，Redis 不可用時仍可使用至到期；Refresh Token 7 天，存 Redis 鍵 `myerp:sys:refresh:{SHA-256}`，值為用戶 Id，以 Lua 原子取出刪除實現輪替。刷新時用戶須仍啟用且未鎖定。
13. 簽章金鑰 `Security:Jwt:SigningKey` 至少 32 bytes，不得提交；非 Development 未設定即拒絕啟動，Development 未設定時用程序內臨時金鑰（ADR-012）。
14. Captcha 萬用碼只在 Development 有效；任何其他環境設定了即拒絕啟動。日誌不記錄密碼、Captcha 答案或 Token。

## 角色、權限與資料範圍（ADR-014）

15. 權限代碼 `{PREFIX}.{RESOURCE}.{ACTION}` 全大寫；前綴必須是宣告模組的前綴。各模組在程式中宣告權限，角色只能授予目錄內的代碼；已不在目錄的舊授權忽略。
16. 角色為全系統定義，用戶在每間公司分別指派角色；必須先有該公司的存取關聯（`sys_user_company`），角色才可指派。
17. 有效權限只計算啟用且未刪除的角色、啟用的用戶公司關聯、啟用且未刪除的用戶與公司。全權角色擁有全部權限，資料範圍為全公司。
18. 同一權限由多個角色授予時取最寬的資料範圍：Self < Department < Branch < Company。分店範圍只看同一分店、部門範圍只看同一部門（不含下級），本人範圍只看負責人為自己的資料；用戶缺少對應的分店／部門歸屬時退回本人。
19. 已登入請求帶的 `X-Company-Id` 必須可存取，否則整個請求回 403，不進入端點；沒有公司上下文的請求不具任何權限代碼。
20. 角色仍被指派時不可刪除，只能停用；停用立即生效。角色修改以 `version` 樂觀鎖，權限集合與角色同一交易更新。
21. 每位用戶最多一間預設公司；設定新的預設公司時，同一交易內先取消其他預設。前端未指定公司時使用預設公司（沒有預設時取代碼最小的公司）。

# SYS 優化記錄

| 日期 | 問題 | 原因 | 改進 | 效果 |
|---|---|---|---|---|
| 2026-10-10 | 組織資料跨公司參照風險 | 單欄 ID 無法防止跨公司指向 | 在 `(company_id, id)` 上加複合鍵與外鍵 | 資料庫阻止跨公司分店與上級參照；違規寫入整合測試通過 |
| 2026-10-10 | 軟刪除代碼可能被重用 | 一般查詢受軟刪除篩選 | 重複代碼檢查明確忽略篩選並以公司 ID 限定 | 已刪除分店代碼重用回 409；有整合測試 |
| 2026-10-10 | 組織代碼可能因空白與大小寫產生歧義 | 資料庫使用不區分大小寫的唯一索引，原服務只檢查長度 | 輸入去空白、轉大寫並限定 ASCII 字元 | 代碼儲存一致；不合法字元在寫入前回驗證錯誤 |
| 2026-10-10 | 組織資料庫約束及實際並發缺少驗證 | 既有測試只覆蓋部分資料表，版本衝突多由同一 DbContext 預檢產生 | 補三表 JSON、分店／部門唯一索引、部門雙 DbContext 並發與公司停用歷史測試 | 13 個組織整合測試通過；未發現需修改服務的缺口 |
| 2026-10-10 | 組織列表翻頁結果可能不穩定 | 相同名稱排序缺乏固定次序，且排序欄位可能未驗證 | 以代碼預設排序，名稱排序加 ID 次序，只接受單一白名單欄位；列表使用無追蹤查詢 | 分頁、關鍵字、隔離及錯誤參數由 SQL Server 整合測試覆蓋 |
| 2026-10-10 | 公司表不受目前公司查詢篩選，直接列舉會洩露其他公司 | 公司是隔離根，不能使用分店／部門的 `CompanyId` 全域篩選 | 內部列表要求授權層傳入可見公司 ID，排除停用及軟刪除公司，排序僅允許 `code`、`name` | SQL Server 整合測試涵蓋未授權公司、停用與軟刪除、空授權、分頁及非法排序；後端 361/361 通過，HTTP 授權待接 |
| 2026-10-10 | 前端骨架可能在無授權時暴露組織入口，且空白名稱可能通過必填檢查 | SYS 權限尚未實作；一般 required 只檢查空字串 | 元件只由輸入資料渲染，不加路由或選單；表單增加非空白名稱校驗，補隔離與校驗測試 | 組織骨架的可見範圍與驗證邊界有元件測試；正式 API 授權仍待 WU-SYS-004 |
| 2026-10-10 | 並發登入錯誤會遺失失敗次數，讓帳號鎖定失效 | 兩個 DbContext 先讀後寫同一計數，最後寫入覆蓋前次 | 改用資料庫原子 `ExecuteUpdate`，條件同時核對雜湊及鎖定狀態，並遞增版本 | 兩個 DbContext 同時錯誤可累計 2 次；四個用戶整合測試通過 |
| 2026-10-10 | 多個 API 同時 401 時，各自刷新會讓後端輪替後的第二個 refresh 失敗並把用戶登出 | Refresh Token 一次即作廢；每個請求獨立呼叫 refresh 會重放舊 Token | `AuthService.refresh()` 以 `shareReplay` 共用進行中的請求，完成後清空；重送失敗直接回錯，不再刷新 | 並發 401 只發 1 個 refresh，兩個請求都以新 Token 重送成功；有單元測試 |
| 2026-10-10 | 登入後 `returnUrl` 可被用作開放重新導向 | 查詢字串可帶 `https://…`、`//host` 或 `/\host` | `safeReturnUrl` 只接受站內 `/` 路徑，排除 `//`、`/\`、`/login` | 9 種輸入有單元測試；登入頁測試確認外部網址登入後回首頁 |
| 2026-10-10 | 攔截器原以 HttpContext 旗標防止重複刷新，多餘且會修改原請求的 context | 重送的請求在 `switchMap` 內，錯誤不會再進入外層 `catchError` | 移除旗標，以結構保證最多刷新一次 | 「重送仍 401 不再刷新」測試通過，程式較簡單 |
| 2026-10-10 | 已登入用戶可偽造 `X-Company-Id` 讀取其他公司資料 | 公司篩選只看標頭，`/me` 這類只需登入的端點不經權限處理器 | 新增 `CompanyAccessMiddleware`，已登入請求的公司必須可存取，否則整個請求 403 | 整合測試確認 `/auth/me` 帶他公司 403；日誌測試以替身授權放行 |
| 2026-10-10 | 同一請求的權限處理器與中介層各自查詢授權 | 兩處都需要用戶在公司的授權 | `ICurrentAuthorization` 以 scoped 快取同一個 Task | 單元測試確認同請求只呼叫 1 次授權來源 |
| 2026-10-10 | 修改角色時版本衝突可能只回滾角色、權限集合已寫入 | 角色列與權限列分兩批 SaveChanges | 改為同一交易內一次 SaveChanges | 舊版本更新回 409 後重新讀取權限不變（整合測試） |
| 2026-10-10 | 持有 `SYS.COMPANY.EDIT` 的用戶可修改任意公司 ID | 公司是隔離根，查詢篩選不適用；權限只看 `X-Company-Id` 的公司 | 修改前檢查目標公司在用戶獲授權的公司內，否則 404（ADR-015） | 整合測試確認改他公司 404，不洩露是否存在 |
| 2026-10-10 | 新公司建立後，建立者切換不到，停用公司也無法重新啟用 | 新公司沒有用戶關聯；授權清單只列啟用公司 | 同一交易建立公司並複製建立者角色；公司列表加 `includeInactive`，範圍取自關聯但不要求公司啟用 | 整合測試覆蓋建立後立即可存取、停用後隱藏、勾選後列出及重新啟用 |
| 2026-10-10 | 控制器直接回傳實體會外露審計欄位（created_by 等） | 服務回傳 EF 實體 | 加入回應 DTO 與 `PagedResultMapping.Map` 擴充方法 | Swagger 只描述 id、code、name、isActive、version（部門另有參照） |
| 2026-10-10 | 重新載入權限時列表多查一次 | `setCompanies` 換掉公司物件，effect 追蹤物件參照 | 改為追蹤公司 ID 的 computed | 單元測試以 `controller.verify()` 確認沒有多餘請求 |
| 2026-10-10 | 骨架列表以本地資料篩選，無法支援大量資料與伺服器端授權 | WU-SYS-001 第一段在授權前只做本地元件 | 改為 nz-table 伺服器端分頁／排序；骨架的「本地篩選、未授權前不開路由」測試改為「伺服器端查詢、路由有 VIEW 守衛」 | 測試範圍沒有縮小：公司隔離改由後端整合測試與 E2E（切換公司）驗證 |
| 2026-10-11 | 用戶 API 關鍵字比對可能受定序影響大小寫 | `username` 欄位定序未保證不分大小寫 | 列表改以 `normalized_username` 比對大寫關鍵字並以其排序（有唯一索引），同值以 ID 穩定排序 | 小寫帳號以大寫關鍵字可查到；排序與分頁由 SYS-USER-011、SYS-USER-015 覆蓋 |
| 2026-10-11 | 管理員可能停用自己或以重複帳號接管他公司用戶 | 用戶為全系統身分，公司範圍只靠用戶公司關聯 | 不可停用自己（422）；重複帳號一律 409、不自動加入本公司；範圍外 404（ADR-016） | SYS-USER-011、SYS-USER-012、SYS-USER-015 覆蓋；後端 420/420 |
| 2026-10-11 | 新增用戶時帳號前後有空白會被前端格式檢查擋下，與後端「去除空白後檢查」不一致 | 表單用 `Validators.pattern` 檢查原始值 | 改用自訂驗證器，先去除前後空白再比對 `USERNAME_PATTERN`，送出時同樣去除空白 | 單元測試以 ` Alice ` 送出得到 `Alice`；E2E 以 ` mary.chan ` 建立成功 |
| 2026-10-11 | 新增或重設密碼失敗後，密碼仍留在對話框欄位 | 失敗時只顯示錯誤，沒有處理表單 | API 失敗後清空密碼與確認密碼並取消 touched 狀態；關閉對話框時重設整個表單 | 單元與 E2E 測試確認 409 後密碼欄位為空 |
| 2026-10-11 | 連按列上操作會重複送出停用或解鎖 | 按鈕沒有進行中狀態 | `busyId` 記錄進行中的用戶，期間其他列操作直接忽略、按鈕停用；對話框保存中亦忽略重複送出 | 單元測試確認進行中再按解鎖不送出、重設密碼連按只送 1 次 |
| 2026-10-11 | 用戶 API 的 REQ_F4118.23.5–8 在一致性報告中沒有資料結構追溯 | WU-SYS-002 第二段只更新 requirements.md 與 api.md | `sys_user` 補上 23.5–8，`sys_user_company` 補上 23.5、23.6（列表範圍與建立時加入公司） | docgen Warning 由 23 降回 19，0 Error |
| 2026-10-11 | 第一個渲染 nz-table 的用戶頁測試在整體並行執行時曾超過 5 秒逾時，單獨執行約 1 秒 | 冷啟動時 transform 與其他測試檔競爭 CPU | 只把該測試的逾時放寬為 15 秒，斷言不變 | 前端全部測試兩次執行均通過 |
| 2026-10-11 | 用戶公司授權 PUT 可指定任何用戶與任何公司（ADR-016 待辦），公司管理員可以接管他公司帳號，或在未獲授權的公司授予全權角色 | 端點只檢查目前公司內的 `SYS.USER.EDIT` | 新增 `AssignInScopeAsync`，要求用戶屬於目前公司、目標公司在操作者授權清單內，否則 404；也不可停用自己的授權（ADR-017） | 整合測試 SYS-PERM-017：越權請求 404／422，且授權沒有改變 |
| 2026-10-11 | 用戶權限頁需要讀取現有指派，逐公司查角色會產生 N+1 | 新查詢端點 | `ListAssignmentsInScopeAsync` 固定用 3 次查詢（範圍、關聯＋公司 join、角色），在記憶體分組 | SYS-PERM-018 通過；查詢次數與公司數無關 |
| 2026-10-11 | 角色頁的 i18n key 原本用 `scope.Self` 等 PascalCase，違反 key 一律 camelCase 的檢查 | 直接拿後端列舉值當 key | 新增 `dataScopeKey()`，把列舉值轉成 `sys.role.scope.self` 等 key | i18n-keys 測試通過 |
| 2026-10-11 | E2E 中第二次刪除時找到 2 個 popconfirm 確認按鈕（strict mode） | 已關閉的 popconfirm 仍留在 CDK overlay | E2E 只點可見按鈕中最後一個（`visible=true` + `last()`；第一個 popconfirm 淡出期間仍算可見，曾偶發失敗） | 角色 E2E 5 個通過，全套 E2E 連續兩次通過 |
| 2026-10-11 | 登入、組織、用戶、角色四個頁面各有一份幾乎相同的錯誤代碼對應函式，新增 429 要改四處 | 每個工作單元複製前一頁的寫法 | 抽出共用 `core/http/api-error.ts` 的 `apiErrorKey(error, knownCodes, validationKey)`，429 一律對應 `errors.COMMON.REQUEST.RATE_LIMITED`；四個函式改為一行呼叫 | 既有錯誤對應測試不變且通過，新增 10 個共用函式測試（WU-SYS-005） |
| 2026-10-11 | 在嚴格 CSP（`script-src 'self'`）下 production 前端整頁沒有樣式，37 個 E2E 失敗 | Angular critical CSS 內嵌（beasties）產生一段內嵌腳本，把樣式表從 `media="print"` 切回 `all`，被 CSP 擋下 | production 設定 `optimization.styles.inlineCritical: false`（ADR-018） | 全部 41 個 E2E 在 CSP 下通過，瀏覽器主控台沒有 CSP 違規 |
| 2026-10-11 | 如果 ForwardedHeaders 沒有設定 Proxy 仍然註冊，任何人都能以 X-Forwarded-For 偽造 IP，繞過按 IP 的限流 | 框架在 KnownProxies 與 KnownNetworks 都空時不檢查來源 | 沒有設定 Proxy 時不呼叫 `UseForwardedHeaders`；有設定時先清空預設的 loopback | SYS-SEC-008、009：偽造的 X-Forwarded-For 不影響計數 |
| 2026-10-11 | 限流若放在公司存取檢查之後，被拒絕的請求仍會先查一次資料庫 | 中介層順序 | 限流放在 JWT 驗證之後、公司檢查之前；CORS 放在限流之前，預檢不計數 | SYS-SEC-006：10 次預檢後仍可登入 5 次 |

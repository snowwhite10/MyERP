# FI business rules

## WU-FI-000d customer credit boundary (planned)

- BR-FI-001: FI owns company/customer credit limits and posted open AR. SD owns Approved, uninvoiced order commitments. `ICustomerCreditService` returns only FI data; consumers never read `ar_` or `gl_` tables.
- BR-FI-002: The credit snapshot uses the current company base currency and server `IClock.Today`. It contains company/customer IDs, currency, effective limit, posted open AR, evaluation date, read timestamp/version and availability reason. A missing or overlapping effective limit, missing company currency, negative/overflowed exposure, mismatched identity/currency or unavailable provider fails closed. An explicit zero limit is valid.
- BR-FI-003: The FI-owned lock key is `(companyId, customerId)`. It must be acquired in the caller's existing SQL transaction before FI exposure and SD commitment reads. Limit edits, AR posting/settlement and SD order decisions use that lock; same-key calls serialize, distinct keys may proceed. The database, rather than an in-process mutex, enforces it across API instances. Lock timeout is a named retryable failure, never permission to approve.
- BR-FI-004: Effective credit periods use inclusive business dates. At most one active approved limit matches a date. A deactivated or soft-deleted record retains history and its code/identity; it cannot silently make an older overlapping row effective. The write path locks the credit key, checks overlap and version, then audits the decision.
- BR-FI-005: FI open AR includes only committed posted receivables less committed allocations, credit notes and reversals. Draft/Pending, failed and rolled-back documents contribute zero. A replay of the same source cannot add exposure again. The future AR posting unit must prove this with real SQL and the same credit lock.
- BR-FI-006: Read-only preview is advisory. SD order submit and SYS final approval must reread under lock in their own transaction; no client-supplied limit, AR amount, timestamp or decision is trusted. FI contract failure blocks SD approval with a named reason. No partial result or success indication is returned for a failed write.

These are design decisions. WU-FI-001a/b owns migration, production contract, authorised HTTP and real SQL verification; WU-SD-006b owns the combined SD decision and override.

## WU-FI-002d sales invoice and return sources (planned)

- BR-FI-007: FI accepts only a persisted SD invoice or Posted return through its public application contract. The caller supplies an immutable source ID, source version and canonical payload fingerprint; FI verifies the saved source through an SD-owned read contract within the same transaction, rather than reading `sal_` tables. A mismatch, missing source or source still pending fails closed. The invoice may be in the SD issuing transaction before its final Posted state; FI verifies its saved issuing state and the caller marks it Posted only after FI succeeds, still in that transaction.
- BR-FI-008: Invoice source uniqueness is `(companyId, SD, Invoice, invoiceId)` and return-credit uniqueness is `(companyId, SD, Return, returnId)`, including soft-deleted history. FI saves the fingerprint and stable posting ID with the source. Identical replay returns the committed result marked unchanged; changed payload is 409. A timeout is resolved by source-key lookup in a fresh transaction before retry. An uncommitted duplicate cannot be reported as success.
- BR-FI-009: Invoice posting uses the saved original-currency and base-currency net, tax and gross from SD, with checked decimal arithmetic. For each currency `net + tax = gross`; FI verifies the independently saved component totals, currency/rate identity and permitted, active MD accounts via MD's public contract. The balanced base-currency journal debits customer AR for base gross and credits sales revenue and output tax for base net/tax. A zero tax line omits a zero-value tax leg. No implicit suspense or rounding plug is allowed; a nonzero residual is a named 422 error. Tax detail and journal mapping remain FI-owned.
- BR-FI-010: Under the FI credit key lock `(companyId, customerId)`, invoice posting increases posted open AR by base gross and SD releases exactly that invoice's saved base-gross unbilled commitment in the same SQL transaction. FI returns source identity, company/customer, original/base gross, currency and posting ID so SD can compare them before commit. FI does not calculate or edit SD commitments. A missing or insufficient matching commitment, FI error, audit error or mismatched result rolls back both sides; credit exposure cannot transiently become a committed double count.
- BR-FI-011: A credit source contains per-original-invoice-line billed allocations, each with positive quantity and original/base net and tax. FI resolves each original FI posting and checks same company, customer, source currency, invoice line and remaining creditable component balances, counting all committed credits including historical soft-deleted rows. For each component, cumulative credits cannot exceed the saved invoice component; SD supplies its cumulative allocation including exact final remainder and FI verifies the aggregate. One return may reference several invoices but has one FI credit source and journal. Cross-company, wrong invoice and duplicate invoice-line allocation fail atomically.
- BR-FI-012: The credit journal debits sales returns/revenue contra and output-tax liability for base net/tax, and credits AR for base gross. The credit allocation reduces only the linked original receivable's open amount. A return's unbilled portion creates no FI credit and is released only by SD; mixed returns do both in one transaction. A fully allocated/settled original cannot be credited below zero. Existing receipts/allocations and prior credits are included in the open-balance check; a credit after collection needs a separately specified refund or unapplied-credit flow and is rejected here, never silently creates negative AR.
- BR-FI-013: Both posting paths join the caller's SQL transaction and acquire the FI credit key before ordered SD source locks, then FI source/receivable keys in ascending ID order. FI writes its journal through `IGlPostingService`, never directly changes a posted journal, and keeps audit, source, receivable, credit allocation and GL entries atomic with SD, SYS and INV when applicable. A failure after any write rolls back every effect and permanent number; post-commit notifications cannot establish Posted state.
- BR-FI-014: Public source reads are company and SYS-scope restricted; write authority is checked by the SD action and FI's internal caller identity. FI rejects a forged company, customer, source, currency, amount, account or actor/time. Financial history remains immutable; correction requires a new authorised compensating source. An unavailable MD account, FI service, lock, journal mapping or original posting yields a named failure and no success indication. WU-FI-002a/b/c must prove these rules with real SQL before an SD invoice or return may claim Posted.

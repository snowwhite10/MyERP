# FI business rules

## WU-FI-000d customer credit boundary (planned)

- BR-FI-001: FI owns company/customer credit limits and posted open AR. SD owns Approved, uninvoiced order commitments. `ICustomerCreditService` returns only FI data; consumers never read `ar_` or `gl_` tables.
- BR-FI-002: The credit snapshot uses the current company base currency and server `IClock.Today`. It contains company/customer IDs, currency, effective limit, posted open AR, evaluation date, read timestamp/version and availability reason. A missing or overlapping effective limit, missing company currency, negative/overflowed exposure, mismatched identity/currency or unavailable provider fails closed. An explicit zero limit is valid.
- BR-FI-003: The FI-owned lock key is `(companyId, customerId)`. It must be acquired in the caller's existing SQL transaction before FI exposure and SD commitment reads. Limit edits, AR posting/settlement and SD order decisions use that lock; same-key calls serialize, distinct keys may proceed. The database, rather than an in-process mutex, enforces it across API instances. Lock timeout is a named retryable failure, never permission to approve.
- BR-FI-004: Effective credit periods use inclusive business dates. At most one active approved limit matches a date. A deactivated or soft-deleted record retains history and its code/identity; it cannot silently make an older overlapping row effective. The write path locks the credit key, checks overlap and version, then audits the decision.
- BR-FI-005: FI open AR includes only committed posted receivables less committed allocations, credit notes and reversals. Draft/Pending, failed and rolled-back documents contribute zero. A replay of the same source cannot add exposure again. The future AR posting unit must prove this with real SQL and the same credit lock.
- BR-FI-006: Read-only preview is advisory. SD order submit and SYS final approval must reread under lock in their own transaction; no client-supplied limit, AR amount, timestamp or decision is trusted. FI contract failure blocks SD approval with a named reason. No partial result or success indication is returned for a failed write.

These are design decisions. WU-FI-001a/b owns migration, production contract, authorised HTTP and real SQL verification; WU-SD-006b owns the combined SD decision and override.

## WU-FI-002d sales invoice and return sources (planned)

- BR-FI-007: FI accepts only a persisted SD invoice or Posted return through its public application contract. The caller supplies an immutable source ID, source version and canonical payload fingerprint; FI verifies the saved source through an SD-owned read contract within the same transaction, rather than reading `sal_` tables. A mismatch, missing source or source still pending fails closed. The invoice may be in the SD issuing transaction before its final Posted state; FI verifies its saved issuing state and the caller marks it Posted only after FI succeeds, still in that transaction.
- BR-FI-008: Invoice source uniqueness is `(companyId, SD, Invoice, invoiceId)` and return-credit uniqueness is `(companyId, SD, Return, returnId)`, including soft-deleted history. FI saves the fingerprint and stable posting ID with the source. Identical replay returns the committed result marked unchanged; changed payload is 409. A timeout is resolved by source-key lookup in a fresh transaction before retry. An uncommitted duplicate cannot be reported as success.
- BR-FI-009: Invoice posting uses the saved original-currency and base-currency net, tax and gross from SD, with checked decimal arithmetic. For each currency `net + tax = gross`; FI verifies the independently saved component totals, currency/rate identity and permitted, active MD accounts via MD's public contract. The balanced base-currency journal debits customer AR for base gross and credits sales revenue and output tax for base net/tax. A zero tax line omits a zero-value tax leg. No implicit suspense or rounding plug is allowed; a nonzero residual is a named 422 error. Tax detail and journal mapping remain FI-owned.
- BR-FI-010: Under the FI credit key lock `(companyId, customerId)`, invoice posting increases posted open AR by base gross and SD releases exactly that invoice's saved base-gross unbilled commitment in the same SQL transaction. FI returns source identity, company/customer, original/base gross, currency and posting ID so SD can compare them before commit. FI does not calculate or edit SD commitments. A missing or insufficient matching commitment, FI error, audit error or mismatched result rolls back both sides; credit exposure cannot transiently become a committed double count.
- BR-FI-011: A credit source contains per-original-invoice-line billed allocations, each with positive quantity and original/base net and tax. FI resolves each original FI posting and checks same company, customer, source currency, invoice line and remaining creditable component balances, counting all committed credits including historical soft-deleted rows. For each component, cumulative credits cannot exceed the saved invoice component; SD supplies its cumulative allocation including exact final remainder and FI verifies the aggregate. One return may reference several invoices but has one FI credit source and journal. Cross-company, wrong invoice and duplicate invoice-line allocation fail atomically.
- BR-FI-012: The credit journal debits sales returns/revenue contra and output-tax liability for base net/tax, and credits AR for base gross. The credit allocation reduces only the linked original receivable's open amount. A return's unbilled portion creates no FI credit and is released only by SD; mixed returns do both in one transaction. A fully allocated/settled original cannot be credited below zero. Existing receipts/allocations and prior credits are included in the open-balance check; a credit after collection needs a separately specified refund or unapplied-credit flow and is rejected here, never silently creates negative AR.
- BR-FI-013: Both posting paths join the caller's SQL transaction and acquire the FI credit key before ordered SD source locks, then FI source/receivable keys in ascending ID order. FI writes its journal through `IGlPostingService`, never directly changes a posted journal, and keeps audit, source, receivable, credit allocation and GL entries atomic with SD, SYS and INV when applicable. A failure after any write rolls back every effect and permanent number; post-commit notifications cannot establish Posted state.
- BR-FI-014: Public source reads are company and SYS-scope restricted; write authority is checked by the SD action and FI's internal caller identity. FI rejects a forged company, customer, source, currency, amount, account or actor/time. Financial history remains immutable; correction requires a new authorised compensating source. An unavailable MD account, FI service, lock, journal mapping or original posting yields a named failure and no success indication. WU-FI-002a/b/c must prove these rules with real SQL before an SD invoice or return may claim Posted.

## WU-FI-003d purchase invoice payable source (planned)

- BR-FI-015: FI accepts only a persisted PUR invoice in Matched state, with every price/tax dispute accepted and still valid. FI reads its saved version, company, supplier, purchase order, receipt allocations, currency and amount components through a PUR-owned contract in the caller's transaction. It never queries `pur_` tables or trusts caller totals. PUR retains the source locks and rechecks net receipt quantity before calling FI; FI does not decide receipt availability. A Draft, Disputed, Rejected, deleted or already Posted source cannot create a new payable.
- BR-FI-016: The permanent source key is `(companyId, PUR, PurchaseInvoice, purchaseInvoiceId)` including soft-deleted history. FI stores canonical fingerprint, saved PUR source version and stable payable/journal IDs. Identical committed replay returns `changed=false` without another payable, journal, audit or quantity change. Different fingerprint or stale version returns 409. If the caller times out, it reads the committed source by key in a fresh transaction; absent means retry the original command, never invent a new source ID. An in-flight row is not success.
- BR-FI-017: FI independently checks each saved line and aggregate original/base net, input tax and gross with checked decimal arithmetic, `net + tax = gross`, source currency and company base currency. FI uses PUR's saved order exchange/tax snapshots and accepted invoice amounts, including preserved benchmark/difference/reason; it does not use current MD rates or silently accept a mismatch. Rounding follows saved line components and an exact final remainder, without a balancing plug. A zero tax component omits a zero-value GL leg.
- BR-FI-018: The balanced base-currency journal debits the configured purchases/expense or purchase-clearing account for base net and input-tax account for base tax, then credits AP control for base gross. FI selects a versioned, eligible mapping through MD's public contract; it cannot directly change INV valuation, infer receipt accrual or use a suspense account. If no valid accounting policy exists for a stock receipt, posting fails with a named 422 until GL policy specifies it. Tax is claimable only where the saved tax snapshot and mapping permit it; otherwise the configured nonrecoverable cost mapping is required. Posted journal lines are immutable.
- BR-FI-019: FI creates original and open payable equal to saved gross, with no payment allocation in this slice. Prior source replay does not increase AP exposure. FI returns company, supplier, source/version, original/base gross, currency, payable ID, journal ID and changed flag; PUR compares this result to its saved source before marking Posted. FI posting alone cannot claim a PUR invoice is Posted, and PUR cannot claim Posted without the FI result.
- BR-FI-020: PUR locks purchase order header, receipt lines ascending and invoice header, then FI acquires its source key and FI-owned payable/journal locks. FI must not call back for PUR locks after taking its source lock; the saved-source verification occurs before that lock. Source, payable, GL, PUR reserved-to-invoiced conversion, state and audit share one SQL transaction. Any error, including after FI writes or before PUR state save, rolls back everything and number allocation. External notifications run only after commit.
- BR-FI-021: PUR's `PUR.INVOICE.POST` authority and SYS data scope guard the command; FI also authenticates the internal caller. FI read uses separate `AP.PURCHASE_SOURCE.VIEW` and company/SYS scope. Cross-company, out-of-scope or forged supplier/source IDs are hidden or rejected, never mapped to another company's AP. Format errors are 400, version/fingerprint conflicts 409, ineligible account/source/mapping or unbalanced components 422, unexpected 500 carries traceId. No batch partial success or implicit skipped line exists.
- BR-FI-022: Posted purchase invoice, FI source, payable origin and GL journal remain traceable and immutable. A subsequent purchase return against invoiced receipt quantity needs a separately specified FI debit/credit note and payable allocation flow before the return can be approved; this slice must reject such a return rather than edit the posted source or create negative AP. Payments and write-offs will later reduce open payable through new immutable allocations, never by rewriting the origin.

## WU-FI-004d GL posting foundation (planned)

- BR-FI-023: FI owns accounting periods and every `gl_` write. Periods are per company with inclusive business dates, Open/Closed state and optimistic version. Creation, date changes and close/reopen use a SQL company period lock and reject overlap even under two connections. Posting uses the saved source business date, never client time or `IClock.Today`, and requires exactly one Open period; absent, ambiguous or Closed period is a named failure. Closing a period does not rewrite its Posted journals; moving/deleting a period that contains one is prohibited.
- BR-FI-024: `IGlPostingService` is the sole FI-owned application write path for journals. SD/PUR and other modules call their FI source contract, which then calls GL; they cannot call GL with arbitrary lines or write `gl_` tables. GL joins the caller's existing SQL transaction and takes source/period locks in a documented order before writing. It cannot commit independently or use a post-commit event to establish Posted state.
- BR-FI-025: A posting request identifies an already saved source by `(companyId, module, sourceType, sourceId, sourceVersion)` and canonical payload fingerprint. FI verifies it through the owning module's public read contract before taking its permanent GL source key; company, actor, currency, business date, accounts and amounts are derived from saved source and FI mapping, never trusted from an HTTP client. The period and all entries belong to the same company and company base currency.
- BR-FI-026: A journal has at least two nonzero lines; each line has exactly one positive debit or credit in base currency `decimal(19,4)`. Checked arithmetic enforces positive equal debit and credit totals within `decimal(19,4)` and prevents overflow. Zero lines, negative amounts, both sides on a line, implicit suspense/rounding plugs and document-currency-only balance are rejected. Per-line document currency amounts, when present, retain the saved source currency/rate and do not replace the base balance test.
- BR-FI-027: FI calls MD `IChartOfAccounts.RequirePostableAsync` for every account at posting time and checks company identity, active status, leaf/postable state and configured mapping version. Duplicate account lines may be aggregated deterministically only if debit/credit direction and accounting dimensions match; otherwise they remain separate. MD owns the account master; FI stores scalar account IDs/codes and immutable account/mapping snapshots, with no cross-module FK or navigation. `IAccountUsage` reports any Posted reference to MD so used accounts cannot be removed or changed incompatibly.
- BR-FI-028: The permanent journal source key includes company/module/type/sourceId across soft-deleted history. Same fingerprint and source version after a committed post returns the same journal and `changed=false`; changed fingerprint/version is 409. Two connections serialize by key. Unknown timeout is resolved by a committed lookup in a fresh transaction; an in-flight result is never called success. Reversal/correction is a new, explicitly authorised source linked to the original, with its own Open period; Posted lines are never edited or deleted.
- BR-FI-029: Journal header, lines, FI source link, AR/AP origin, upstream Posted state, number and audit share one SQL transaction. Any failure, including account/period revalidation, audit write or downstream source comparison, rolls back all writes. No partial line success, skipped line or batch mode exists in this foundation. A no-change replay produces no new audit and must not show a save-success message.
- BR-FI-030: Only authorised source actions can invoke FI posting; internal caller identity is checked. Read APIs require `GL.JOURNAL.VIEW`, company and SYS data scope. Wrong company or out-of-scope IDs are hidden as 404; bad format is 400, version/fingerprint conflict 409, invalid period/account/balance 422, unexpected 500 includes traceId. The future UI displays saved immutable data, an explicit unchanged replay and translated error/timeout states; it never claims Posted from an uncommitted result.

These are design rules only. WU-FI-003a/b/c and WU-FI-004a/b/c must turn them into red/green tests, schema, contracts and authorised reads before PUR-008b can assert Posted.

# PUR 檢查與優化記錄

## WU-PUR-002b2a 資料範圍審查

- 問題：002b1 的列表與詳情只做公司／軟刪篩選，具有 VIEW 權限但授權範圍較窄的用戶仍可看到全公司請購；表頭沒有分店／部門歸屬。
- 原因：當時資料模型只保存請購人，尚未接入 SYS 的有效資料範圍。若直接套共用 `IDataScopedEntity.OwnerUserId` 查詢，請購的請購人別名不能由 EF 轉成 SQL；因此在 PUR 查詢中明確以 `requester_id` 套用本人條件。
- 修改：表頭增加可空歸屬欄位及兩個查詢索引，服務先取得 SYS VIEW 範圍，於 SQL 計數／分頁及詳情讀取前套用；缺 VIEW 回 403，範圍外詳情回 404。真實 SQL 驗四種資料範圍及缺組織時降為本人，真實 HTTP 驗登入 VIEW 200／無權 403／他公司 404。
- 診斷：HTTP 測試首次預期切換至未授權公司會回 404，實際由 SYS 公司授權中介層先回 403。以同一已授權公司查另一公司請購 ID 後驗到 PUR 的 404；這是測試前置設定問題，沒有改產品守衛。
- 限制：既有請購若分店／部門為空，只能由本人或全公司範圍看見；建立端點在 002b2b 須從 SYS 授權寫入歸屬，修改／刪除在 002b2c 套各動作資料範圍。

## WU-PUR-002b1 讀取切片

- 問題：若列表先載入明細再分頁，行數增加時會放大 SQL 與記憶體成本；單筆讀取若只靠路由權限，跨公司 ID 仍可能洩漏。
- 修改：列表在資料庫先套公司／軟刪篩選與白名單排序，再計數和投影當頁的行數；詳情以公司篩選讀取並二次核對表頭公司。回應使用明確 DTO，避免序列化實體導覽及審計欄位。
- 效果與限制：真實 SQL 讀取及 HTTP 匿名守衛通過；已登入細分權限／資料範圍尚未驗。現有表頭沒有部門與分店歸屬，002b2 要補 migration、資料範圍過濾及 HTTP 測試。

## WU-PUR-002a 資料模型審查

- 問題：明細若只以表頭 ID 連結，可能出現跨公司引用；已轉採購量若沒有資料庫約束，後續轉單競態可產生負餘量。
- 原因：請購與後續採購單都按公司隔離，消耗量將由多個交易更新。
- 修改：明細使用 `(company_id,requisition_id)` 同公司複合 FK；`0 ≤ ordered_quantity ≤ quantity` 由 SQL CHECK 守護，表頭與明細各有查詢索引。EF 仍以公司 Global Query Filter 排除他公司資料。
- 效果與限制：真實 SQL 閏日／六位數量與非法負數、他公司不可見測試通過；API 驗證、SYS 單號、MD 引用、版本 409 與資料範圍留 002b。migration 是可回滾的兩表變更，未建立跨模組 FK。

## WU-PUR-001 模組與守衛審查

- 問題：新模組若只在程式檔存在而未加入 API 組合根或 solution，全量測試和權限目錄都可能漏掉 PUR；資料服務若接受缺公司上下文可能誤讀資料。
- 原因：模組組件由 `AddErpModules` 明確註冊，資料服務將由後續切片加入。
- 修改：兩組件加入 solution、API 引用與模組註冊；請購公司守衛對缺公司回 403、不同公司回 404；權限由單一目錄宣告。專項測試涵蓋組件發現、DI、全部權限及零／負公司 ID。
- 效果與限制：本切片沒有資料表或端點，002 仍須驗 EF 公司篩選和 HTTP 403／404，003／004 驗狀態與畫面。紅燈先由缺 PUR 命名空間的編譯錯誤確認。

## WU-PUR-000 設計檢查

- 問題：若請購直接持有庫存或跨模組讀 MD／SYS 表，後續轉採購與收貨可能破壞模組邊界。
- 原因：請購只表示需求，庫存異動屬 INV，物料與審批各有公開契約。
- 修改：需求及 API 明確限制請購無庫存副作用，MD／SYS 只經契約，後續採購入庫經 INV Application 契約；資料模型僅存跨模組 ID。
- 效果與限制：本輪僅固定契約，尚無產品程式、migration 或真實瀏覽器可驗；實作時用 PUR-REQ-001、015 及庫存零異動斷言核實。

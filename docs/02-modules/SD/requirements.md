## WU-SD-002d quotation acceptance detail (design only)

REQ_F4112.1.1–3 retain Version 1.0; this section makes their existing acceptance criteria testable without claiming delivery. A quotation belongs to one company, has a permanent document number and 1–1000 ordered lines. It starts Draft; only Draft or Rejected can be revised, and revision of Rejected returns it to Draft while preserving SYS history. Submission validates references, amounts and an expiry date on or after the business date; it becomes Pending or immediately Approved according to SYS. A final SYS rejection makes it Rejected. An Approved quote may be voided only before conversion, and expiry is computed from `IClock.Today` rather than mutating its stored approval status. Only one order may convert a quote, preserving line source and monetary snapshots. A second conversion or void after conversion returns a specific conflict. Details and list filters show stored status and effective expiry separately; no quotation reserves stock or credit.

The implementation slices must prove company and action scope, document version conflicts, deleted or disabled MD references, no applicable SYS step, concurrent decisions/conversions, rounding and overflow, and whole-document rollback. Quotation print/export is a later interface capability and must not appear as a working action before its own permission, output and tests exist.

## WU-SD-003d order acceptance detail (design only)

REQ_F4112.2.1–6 and REQ_F4112.6.1 retain Version 1.0; these rules make the existing acceptance criteria testable. An order belongs to one company and has a permanent number, business date, approved customer, currency, 1–1000 ordered lines, version and immutable monetary snapshots. A manually created order has no quotation source. Conversion copies every saved line of one Approved, unexpired quotation exactly once in one transaction; source quote and line IDs survive order cancellation and soft deletion. All lines use positive base-unit quantity with at most six decimals, and no draft order reserves or posts stock.

Draft can be edited, submitted or soft-deleted; Rejected can be revised into Draft with earlier SYS rounds retained. Pending allows only SYS decision. Final approval requires a fresh MD/customer and FI/AR credit decision, including any authorised override, in the decision transaction. If FI/AR credit exposure is unavailable, submit/approval is blocked with a named reason and cannot assume zero exposure. Approved permits delivery or cancellation only while no active or posted delivery exists; Cancelled is read-only. Stale versions return 409; other-company or action-scope-excluded IDs return 404. A document write is atomic: invalid line, duplicate source, SYS failure or credit refusal leaves no partial order, number, approval or stock effect. A separate EXPORT permission and safe output are required before enabling an export action.

## WU-SD-004d outbound acceptance detail (design only)

REQ_F4112.3.1–6 retain Version 1.0. Each outbound belongs to one Approved order in the same company. A line references a saved order line and copies its item identity and base-unit quantity; the user selects a valid warehouse, optional location and tracking. Its Draft does not reserve an order balance or change INV. The aggregate available quantity per order line is ordered quantity minus Posted quantity minus all active Pending reservations. Submit locks the affected order lines in ascending ID order and rejects a quantity above the balance; final SYS approval locks and rechecks the balance with the current delivery's own reservation counted once. Rejection releases that reservation once. A Rejected revision returns to Draft and retains SYS history; Posted is immutable. All quantity comparisons use decimal with six fractional places and never use a sales price as an INV cost.

The final approval handler reloads the Pending delivery, company, version and saved lines. Within the SYS decision transaction it calls INV `PostSalesOutboundAsync` with the SD delivery ID and saved date/lines, then marks the delivery Posted and stores the returned movement IDs. A zero-step submission performs the same posting path in the submit transaction. INV rejects insufficient stock, invalid tracking/location and conflicting source snapshots; any failure rolls back the SYS decision, SD state/reservation effect and all INV movements. A repeated decision cannot post again; INV's identical-snapshot replay is a secondary guard, not permission to approve a Posted document. Draft delete uses the current version and does not release a reservation; Pending cannot be edited/deleted, and Posted cannot be deleted or directly reversed. The future return flow uses a new auditable source.

No delivery table, migration, endpoint, handler or screen exists in WU-SD-004d. WU-SD-004a/b/c own implementation and real SQL/HTTP/UI evidence. Change record: WU-SD-004d clarified existing outbound acceptance without changing requirement meaning or Version.

## WU-SD-006d credit acceptance detail (design only)

The FI/AR contract owns one effective credit limit and posted, unsettled receivables for a company/customer, expressed in the company's base currency. Credit evaluation uses `IClock.Today` at submit and final decision; a backdated order cannot select an older limit or AR state. SD owns approved order value that has not yet become a posted receivable. The candidate is counted once: on Draft submit it is added to existing commitments; on Pending final decision it is excluded by order ID from any commitment query before adding its current saved value. Pending orders do not reserve credit. The credit decision is `limit - AR exposure - other SD commitment - candidate >= 0`, using saved rounded base-currency gross amounts and checked decimal arithmetic. A missing limit is a refusal, not unlimited credit. Cancellation, invoicing, settlement and company currency changes must keep component ownership and transitions explicit; no client balance is trusted.

Check again within the SYS final-decision transaction using the same customer credit lock as submit and FI credit mutations. A rejected check leaves the order and SYS decision unchanged. A zero-step approval uses the same check and lock. An override only handles a known numerical over-limit result and requires `SAL.CREDIT.OVERRIDE`, a nonblank reason, current version and approval-round identity. It is recorded once with the measured excess and actor/time; changed exposure requires a fresh decision. Missing FI/AR contract, failed query, stale snapshot, invalid company/currency or inactive/unapproved customer cannot be overridden. UI and API must distinguish these causes.

WU-SD-006a/b/c own FI/AR implementation, SD transaction logic and UI respectively. No credit table, route or screen is delivered by this design section.

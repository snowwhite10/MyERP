WU-SD-002a transaction-store checkpoint (2026-10-29T01:04:58+08:00): `SalesQuotationDraftStore` now saves prepared Draft snapshots, replaces all saved lines under a checked version, and soft-deletes Draft within a caller-owned transaction. WU-SD-003a command race checkpoint (2026-10-28T16:01:39+08:00): authenticated `PUT orders/{id}` commands with the same version serialize on the saved header, returning one 200 and one 409; simultaneous `DELETE orders/{id}` commands return one 204 and one 404. The lock is company constrained, and the specific EDIT/DELETE SYS scope is still checked in the transaction before mutation.


All routes use `/api/v1/sal/` to match the `sal_` module prefix; Swagger groups `SD - Quotations`, `SD - Orders`, `SD - Deliveries`, `SD - Pricing`, `SD - Invoices`, `SD - Credit` and `SD - Returns`. Every route requires the current company and its own `SAL.<RESOURCE>.<ACTION>` permission. Read and write scope follow SYS action data scope before loading a document. Lists use stable server pagination, whitelist sort and date/status/customer filters. 401/403/404/400/409/422/500 use ProblemDetails with `errorCode` and `traceId`.

## WU-SD-002d quotation endpoint detail (planned)

WU-SD-002a must add `SAL.QUOTATION.VOID` before exposing `POST quotations/{id}/void`; the current catalog has no VOID action. No direct SD approve/reject route is planned: SYS approval endpoints produce `ApprovalCompleted` for document type `SAL.QUOTATION`. A no-step submission returns Approved and is handled by SD immediately in the submit transaction. `POST quotations/{id}/submit` and `/void` require a body `version`; rejected revisions use `PUT quotations/{id}` with `version` and the full 1–1000 saved lines. `GET` detail returns version, saved line amounts, SYS history and an `isExpired` flag derived from `IClock.Today`. A converted quote returns its source order link through an SD-owned query.

The create/edit body accepts customer ID, business/expiry dates, currency, positive line quantities, unit price, discount rate and output-tax selection; server resolves company, number, MD snapshots, exchange rate, tax rate and totals. Return 400 for malformed fields/precision, 409 for stale version or duplicate conversion, 422 for expired/status/reference/overflow and 404 for other-company or out-of-action-scope IDs. All writes are atomic. Exact DTOs, Swagger examples and HTTP assertions are delivered with WU-SD-002a. `REQ_IO_A` item IDs are allocated only in WU-SD-002b when actual View/Create/Edit controls are implemented, using each interface's next item number; this design does not allocate any.

## WU-SD-003d order endpoint detail (planned)

`POST orders` creates manual Draft; `SalesOrderCreateService` owns the SYS number, MD snapshot and store transaction. `POST quotations/{id}/orders` converts one complete Approved, unexpired quote using a current quote version, returning the Draft order and source link. `PUT orders/{id}` accepts `{version,draft}` and replaces all Draft/Rejected manual lines, preserving number and source identity; it returns the saved detail. `DELETE orders/{id}?version=...` soft-deletes only Draft and returns 204. Both mutations check their own SYS action scope inside a Serializable transaction; hidden IDs return 404, stale versions 409. `POST orders/{id}/submit` sends Draft to SYS after current MD and FI/AR credit checks; `POST orders/{id}/cancel` requires `SAL.ORDER.CANCEL`, current version, Approved status and no active or posted delivery. SYS approval/rejection endpoints own decisions; SD handles zero-step return and final callback in the same transaction. There is no direct SD approve/reject route or order-side INV posting.

GET list/detail return saved snapshots, status, version, delivery balance and SYS history; GET list has stable pagination and whitelisted date/status/customer sort/filter. Each route checks its exact action permission and SYS data scope before loading the document; a CREATE or EDIT form's MD options must not require `SAL.ORDER.VIEW`. Create/edit input accepts customer, business date, currency, 1–1000 lines and priced quantities; server derives company, number and all totals. A converted order ignores client price overrides and uses saved quote snapshots. Malformed fields/precision give 400, stale version or duplicate conversion 409, invalid state/reference/credit/overflow 422, hidden ID 404, unexpected failure 500 with traceId. `SAL.CREDIT.UNAVAILABLE` is a named block until FI/AR supplies exposure. Exact DTOs, Swagger examples and authorised SQL/HTTP tests belong to WU-SD-003a/b. Export stays unavailable until separate `SAL.ORDER.EXPORT` output and tests are implemented.

## WU-SD-004d outbound endpoint detail (planned)

`GET deliveries` and `GET deliveries/{id}` return saved order/line links, quantities, tracking, state, version, SYS history and INV movement IDs; lists have stable company-scoped pagination and whitelisted order/date/status filters. `POST deliveries` creates a Draft from one Approved order, `PUT deliveries/{id}` replaces all Draft/Rejected lines using `version`, `DELETE deliveries/{id}?version=...` soft-deletes Draft, and `POST deliveries/{id}/submit` takes `version`. Each route uses its exact `SAL.DELIVERY.VIEW/CREATE/EDIT/DELETE/SUBMIT` permission and SYS action scope. Approve/reject stays on SYS approval endpoints; there is no direct client posting route. A CREATE/EDIT form's eligible order, warehouse and tracking options must be authorised for that action without requiring DELIVERY.VIEW.

Create/edit input accepts order ID, saved business date, 1–1000 lines with order-line ID, warehouse/location and positive six-place base-unit quantity plus lot/serial selections; server derives company, number, order/item snapshots and posting source. A delivery may use multiple lines for one order line, but the service aggregates them for balance checks. Client-provided remaining quantity, approval state, INV source, movement IDs and sales-cost fields are ignored/rejected. Submit reserves only while Pending; zero-step approval posts in the submit transaction. Final callback reloads Pending and its saved snapshot, serializes order lines, rechecks balance and calls INV once in the caller's transaction. Rejection releases reservation with no INV call. Return 400 for field/precision/line limits, 404 for hidden company or action-scope IDs, 409 for stale version, concurrent balance or repeated decision, and 422 for order state, insufficient order balance, invalid MD/INV reference, stock or tracking. Unexpected 500 includes traceId; timeout/network failure must not claim success. Exact DTOs, Swagger examples, SQL and authorised HTTP assertions belong to 004a/b.

## WU-SD-005d pricing endpoint detail (planned)

WU-SD-005a adds `SAL.PRICING.CREATE`, `EDIT`, `DEACTIVATE` and `OVERRIDE` to the permission catalog, then implements company/scope-bound `GET /price-rules` (stable paged filter by item/customer/currency/date/status), `GET /price-rules/{id}`, `POST /price-rules`, `PUT /price-rules/{id}` with required version, and `POST /price-rules/{id}/deactivate` with version. Rule writes reject same-key overlapping active inclusive periods under a SQL serialization guard; a stale version or concurrent overlap returns named 409. Other-company/out-of-scope IDs return 404. Current proposal makes an authorised rule write active immediately; if SYS approval is required by later business policy, a separate ADR and work unit must define that workflow before exposing it. All mutations audit old/new price, ceiling, dates, actor and time.

`GET /price-rules/quote?customerId=&itemId=&currency=&businessDate=` requires `SAL.PRICING.VIEW` or the matching `SAL.QUOTATION.CREATE/EDIT` or `SAL.ORDER.CREATE/EDIT` action for a form. It returns one selected customer-specific or default rule plus ID, version, price, ceiling, effective dates and `asOf`; it writes nothing. A missing rule is 422 `SAL.PRICING.RULE_NOT_FOUND`; malformed date/IDs 400; hidden company/customer/item 404; duplicate active candidates 409 integrity error. It never accepts a client-supplied company ID. Bound paging applies to lists, not this single lookup.

Quotation/manual-order save bodies may carry `pricingRuleId`, `pricingRuleVersion`, `unitPrice`, `discountRate` and optional `overrideReason`; the server treats the first two as concurrency hints, resolves the current business-date rule again and derives all amounts. An absent/stale hint after a displayed quote is 409 `SAL.PRICING.STALE_QUOTE`; a manual price, no matching rule or discount above ceiling without `SAL.PRICING.OVERRIDE` is 403, and an override without a reason is 400. For a granted override the response contains saved rule/provenance, amount snapshot and document version. Converted orders copy the saved quote snapshot and ignore pricing hints. Error DTOs include line/field paths; 500 includes traceId. Exact DTOs, Swagger examples, SQL/HTTP assertions and migration are WU-SD-005a gates; UI is WU-SD-005b.

## WU-SD-006d credit endpoint and FI contract detail (planned)

FI/AR's public `ICustomerCreditService` proposal has `GetSnapshotAsync(companyId, customerId, evaluationDate)` and a transaction-scoped `AcquireCreditLockAsync(companyId, customerId)` operation. The server supplies `IClock.Today` as evaluation date at each decision; a client or backdated order cannot select historic headroom. The snapshot returns base currency, effective limit, current posted open AR, as-of date, FI version and an explicit availability/error state. FI owns the database rows and lock; SD never reads FI tables. FI credit mutations must use the same lock. Implementation may refine names/signatures in 006a without weakening the company, currency, transaction or fail-closed guarantees. Missing service/snapshot returns `SAL.CREDIT.UNAVAILABLE`; absent effective limit returns `SAL.CREDIT.LIMIT_NOT_SET`; invalid or stale data returns `SAL.CREDIT.INVALID_SNAPSHOT`. All block submit/final approval and cannot be overridden.

`GET /api/v1/sal/credit-checks/{customerId}?orderId=` is an advisory, read-only check using the server's current evaluation date. `SAL.CREDIT.VIEW` permits a company/scope-bound customer check; an order action holder may check only that order in its exact action scope. The response includes company base currency, FI limit/open AR, other SD commitment, candidate saved gross, headroom, exceeded amount, FI as-of/version, decision/reason and `requiresRecheck=true`; no FI document detail. It makes no audit or order change and never gives a save-success toast. Other-company or hidden customer/order returns 404, absent permission 403, bad ID 400, unavailable/invalid FI data 422 with named codes, unexpected failure 500 with traceId.

`POST orders/{id}/submit` accepts the order version and optional `creditOverrideReason`; SYS final decision carries any separately authorised override request bound to the current order version/round. The server ignores client limit/exposure/actor/time/decision fields. Known over-limit without grant returns `SAL.CREDIT.LIMIT_EXCEEDED` (422, measured excess); missing `SAL.CREDIT.OVERRIDE` for a supplied reason returns 403, blank reason 400, stale order/FI snapshot or changed round 409. `SAL.CREDIT.OVERRIDE` never replaces `SAL.ORDER.SUBMIT` or SYS `SYS.APPROVAL.PROCESS`. The service rechecks under the FI credit lock in the submit/final-decision transaction; on failure no order/SYS state or override record persists. A successful response returns the saved decision and audit reference. Exact DTOs, Swagger examples and authorised SQL/HTTP tests belong to 006a/b, with UI in 006c.

## WU-SD-007d invoice endpoint and FI contract detail (planned)

`GET /api/v1/sal/invoices` and `GET /api/v1/sal/invoices/{id}` require `SAL.INVOICE.VIEW`, apply current company and SYS action scope before query, and return stable paged summaries or immutable detail with saved source lines, tax/amount snapshots, FI posting reference, version and request key. `GET /api/v1/sal/deliveries/{id}/invoiceable-lines` requires `SAL.INVOICE.ISSUE` in that source's action scope; it returns Posted saved quantity, already billed quantity and current balance as an advisory view. No GET causes a success toast or data change.

`POST /api/v1/sal/invoices` requires `SAL.INVOICE.ISSUE`, an idempotency request key (bounded opaque client value), business date, one to 1000 `{deliveryLineId, quantity}` lines and no client amount, tax, FI reference or state. Server derives company/customer/order/currency from the first source and requires every line to match. It locks FI credit key first, then SD order/source line IDs in ascending order, checks aggregate delivered and previously billed quantities, allocates saved net/tax, assigns a permanent number, calls FI/AR `PostSalesInvoiceReceivableAsync` with source `(SD,Invoice,invoiceId)`, customer, saved base-currency gross and tax breakdown in the same transaction, and persists matching FI posting ID. FI must return source, currency and amount for verification. Only a committed invoice and FI posting yield `201`; identical request replay returns the saved invoice with replay indication and zero-change warning semantics, while changed payload under the same key is 409. Unknown timeout prompts a GET by request key before any retry; 007a fixes the precise request/response DTOs and Swagger examples.

Malformed fields/precision/line count give 400, missing action 403, hidden source 404, stale source balance or request-key conflict 409, invalid source status/quantity/tax/FI unavailable 422, and unexpected 500 includes traceId. FI timeout/error rolls back the whole SD/FI transaction; no persisted invoice or success message. No direct SD approve/edit/delete route exists for Posted invoice. Credit note/reversal is a separate future work unit. SQL, authorised HTTP, lock order, FI result matching and rollback belong to 007a; UI to 007b. No endpoint is delivered by this design section.

## WU-SD-008d return endpoint and INV/FI contract detail (planned)

`GET /api/v1/sal/returns` and `GET /api/v1/sal/returns/{id}` require `SAL.RETURN.VIEW`, stable company/scope pagination and saved SD/INV/FI references. `GET /api/v1/sal/deliveries/{id}/returnable-lines` requires `SAL.RETURN.CREATE` in that source's action scope and returns Posted, invoiced, prior returned and unbilled balances as an advisory snapshot. `POST /returns` creates Draft; `PUT /returns/{id}` replaces Draft/Rejected lines with version; `DELETE /returns/{id}?version=` soft-deletes Draft; `POST /returns/{id}/submit` sends Draft to SYS with version. Add `SAL.RETURN.EDIT/DELETE/SUBMIT` to the permission catalog in 008a. SYS endpoints decide Pending approval/rejection; there is no direct client INV/FI posting route.

Create/edit accepts opaque request key, one to 1000 lines with Posted delivery-line ID, positive six-place return quantity, destination warehouse/location/tracking, unbilled quantity and `{invoiceLineId,quantity}` billed allocations. Server derives company, customer/order, original outbound movements, source snapshots, number, cost, tax, credit and actor. It rejects client cost/credit/status/source-company fields. The final callback obtains FI credit lock, then SD order/source locks, rechecks balances, posts new INV `SALES_RETURN` through an extension of `IExternalInventoryPostingService`, posts FI credit for billed portions through a FI public contract, releases SD unbilled commitment, verifies returned IDs/amount/currency/source, then marks Posted in the same transaction. Zero-step SYS submit executes the same sequence; rejection posts neither service. Exact contract method names, DTOs, Swagger examples and real SQL/authorised HTTP tests belong to 008a.

Malformed quantity, partition, precision, line count or key gives 400; missing action 403; other-company/out-of-scope source 404; stale version, concurrent balance or changed request-key payload 409; unposted source, unsupported tracking, missing original cost, unavailable INV/FI or mismatched result 422; unexpected 500 includes traceId. Identical committed replay returns existing result with `replayed=true` and zero-change semantics. After timeout, GET by request key must determine whether the transaction committed before retry. No endpoint is delivered by this design section.
## WU-SD-009d internal demand reader design (no endpoint)

`IApprovedDemandSnapshotReader` is planned for `MyERP.Modules.Sales.Contracts`, to be implemented in WU-SD-009a after real SQL tests. Request: caller/company and authorised scope, inclusive `fromMonth`, exclusive `toMonth`, optional item/site filters, `cursor?`, `pageToken?`, `pageSize` 1–500.

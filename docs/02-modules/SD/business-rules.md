- BR-SD-001: SD owns quotations, orders, deliveries, invoices and returns. MD supplies customer, item, currency, output-tax and payment references through Contracts. SD stores commercial snapshots and never reads MD tables directly.

WU-SD-003a MD identity checkpoint (2026-10-27T16:10:46+08:00): `ISalesItemLookup.RequireActiveAsync` returns the current-company active item ID/code/name for a future order-line snapshot. Missing, soft-deleted or foreign items return `MD.ITEM.NOT_FOUND`; inactive items return `MD.ITEM.INACTIVE`. Customer identity, currency/rate and output tax already have separate MD Contracts. The order command must still resolve all references and save them with SYS numbering in one transaction; this lookup alone does not hold a lock against concurrent MD changes.
- BR-SD-002: SYS owns company-scoped numbering, permissions, data scope and approval decisions. Each SD action checks its own permission and action scope; a VIEW permission is not required for a CREATE/EDIT-only workflow. Every document preserves approval history and audit/version fields.
- BR-SD-003: Quotation conversion is explicit and single-use. The order retains immutable quotation and line source IDs plus price, discount, tax and currency snapshots. Quotation draft or expiry cannot be converted. No quotation action changes stock.
- BR-SD-004: Order approval revalidates current customer and credit through public contracts before SYS final decision. With FI/AR not yet available, approval must fail with a specific unavailable-credit reason; no fabricated exposure or silent bypass. Approval alone does not post INV.
- BR-SD-005: Each delivery line refers to an approved order line; summed posted quantity plus active pending delivery quantity must not exceed ordered base-unit quantity. Lock order lines in ascending ID order and recheck during submit and final approval. Draft does not reserve or post stock.
- BR-SD-006: Final SYS delivery approval, SD Posted state and `IExternalInventoryPostingService.PostSalesOutboundAsync` run in one SQL transaction. SD provides saved item/warehouse/location/basic-unit quantity/tracking, never sales price as cost. INV owns negative-stock, serial/batch, duplicate-source and ledger rules (BR-INV-040–042); a failure rolls back every module's changes.
- BR-SD-007: Rejection releases any delivery reservation once; repeated decision or retry cannot post twice. Posted delivery is immutable. Corrections use a new return/reversal source, never direct INV aggregate updates. Return source type requires an explicit future INV contract extension.
- BR-SD-008: Monetary lines use decimal, saved output tax and currency rate effective on business date, and `Money.Round` at currency precision. Sum already rounded line values for header totals. Existing snapshots never change because a master rule changes.
- BR-SD-009: Invoices cover only posted, uninvoiced delivery quantity. SD owns commercial invoice; FI owns receivable/posting and consumes SD via its public interface when available. SD must not write FI tables. Credit exposure likewise comes from FI/AR, never from direct reads.
- BR-SD-010: All writes are whole-document atomic; no silent skip or partial success. Repeated code, deleted/disabled reference, stale version, invalid status and cross-company source produce specific errors. List/export and UI messages must reflect saved data, including zero changed records.

These rules are design decisions for later implementation, not claims of working functionality. Legacy source, if consulted later, supplies business understanding only; no code or schema is copied.

## WU-SD-002d quotation decisions (planned)

- BR-SD-011: Quote states are `Draft`, `Pending`, `Rejected`, `Approved`, `Voided`. Creation is Draft. Edit is allowed from Draft or Rejected with the current version; editing Rejected resets it to Draft but keeps all prior SYS rounds. Submit is allowed from Draft only, after rechecking the approved customer and active item/currency/output-tax references. Pending cannot be edited, deleted, voided or submitted again. Final SYS `IApprovalResultHandler` maps approval/rejection to Approved/Rejected within the SYS transaction. A zero-step SYS `SubmitAsync` returns Approved immediately and SD must set its own status in the same transaction; SYS does not call the handler in that case.
- BR-SD-012: `expiry_date` is inclusive. It must be at least the quotation business date on save; submission and conversion additionally require `IClock.Today <= expiry_date`. Approval status remains Approved after expiry for audit; the API also returns an `isExpired` derived flag. Do not use a background mutation to mark expiry. A voided quote stays visible in history. Only an Approved, unexpired, unvoided quote can convert.
- BR-SD-013: One quote converts to at most one order, including when the order is later soft-deleted or cancelled. The future order header stores immutable `source_quotation_id` and each order line stores immutable `source_quotation_line_id`; unique database constraints on these links include soft-deleted rows. Convert locks the source in the same transaction, validates company and version, and creates the order with all saved lines. No partial line conversion is supported in the first quote-to-order flow. A second concurrent conversion loses with 409; no order or number is retained from the losing transaction. Direct order creation has null source IDs.
- BR-SD-014: Quote save snapshots MD item identity, item code/name, currency, effective output tax rate and exchange rate; reference IDs are verified through MD Contracts on create/edit/submit. The client supplies a nonnegative unit price with at most six decimal places, a discount rate from 0 to 100 with at most four decimal places, and a positive base-unit quantity with at most six decimal places. For each line, `net = Money.Round(quantity * unitPrice * (1 - discountRate / 100), currency)`; `tax = Money.Round(net * taxRate / 100, currency)`; `gross = net + tax`. Convert each rounded original-currency amount to base currency at the saved rate, then `Money.Round(..., baseCurrency)` per line; header totals sum saved rounded line amounts. Reject decimal overflow before persistence; do not silently truncate. Tax and exchange rate selection use the quotation business date, not the current date. Later MD changes cannot recalculate saved values.
- BR-SD-015: `SAL.QUOTATION.SUBMIT` authorises submission, while approval/rejection uses SYS `SYS.APPROVAL.PROCESS`. Draft soft delete requires `SAL.QUOTATION.DELETE` and current version; void requires a distinct `SAL.QUOTATION.VOID` permission and only Approved without a source order. These new action codes are a design target for WU-SD-002a, not present in the current permission catalog. All lookups apply current company and the exact action's SYS data scope before revealing a quote. Whole-document failures leave neither quote rows nor SYS approval changes; audit records each accepted transition.

## WU-SD-003d order decisions (planned)

- BR-SD-016: Order states are `Draft`, `Pending`, `Rejected`, `Approved`, `Cancelled`. Create is Draft; edit of Rejected returns Draft and retains SYS history. Draft may be deleted; only Draft may submit. SYS final decision maps Pending to Approved/Rejected in its transaction. A zero-step SYS submit may approve immediately only after the same credit check succeeds. Pending/Approved/Cancelled content is immutable. Every command requires its exact `SAL.ORDER.*` permission, current company, action data scope and version.
- BR-SD-017: Manual create and quote conversion share one amount/snapshot policy: MD customer/item/currency/output-tax references and dated rate are resolved through public contracts, then line original/base net, tax and gross are rounded with `Money.Round` before header summation. Conversion copies the saved quote commercial snapshot and all lines without recalculating against changed MD prices or rates. Source quote/line IDs are immutable, unique including soft-deleted orders, and same-company. Lock quote before conversion, use a database unique constraint as the final concurrent guard, and roll back the losing number and document.
- BR-SD-017 implementation checkpoint: `SalesOrderSnapshotBuilder` prepares the manual snapshot through MD public contracts and uses the company's currency precision for line rounding. `SalesOrderCreateService` checks `SAL.ORDER.CREATE`, then allocates the SYS number, resolves the snapshot and saves it through `SalesOrderDraftStore` in one transaction. Existing quote conversion remains separate. MD reference stability under concurrent edits still requires real-MD SQL verification.

WU-SD-003a data-scope checkpoint: manual create persists the SYS action authorization's user, branch and department on the order header. Existing rows inherit their creator as owner during migration. Read/edit/delete action scope still needs to be enforced by the authorised HTTP and command paths.

WU-SD-003a command checkpoint (2026-10-28T14:59:03+08:00): manual edit and delete now check their exact SYS action scope against the saved header in a Serializable transaction before calling the versioned draft store. EDIT rebuilds MD snapshots and replaces lines; DELETE soft-deletes Draft only. The focused real-SQL test covers Branch-hidden IDs and old-version conflict. Authorised HTTP and concurrent command races remain open.

WU-SD-003a list checkpoint (2026-10-28T15:06:01+08:00): the VIEW list applies the actor's company and SYS data scope before filters, count, stable sort and page projection. Equal business dates are ordered by immutable ID, so separate pages do not repeat rows when the data is unchanged. A hidden scope returns an empty page without revealing the total from another scope.
- BR-SD-017 MD stability checkpoint (2026-10-27T16:37:47+08:00): manual create now uses a Serializable transaction for the SYS number, MD contract reads and SD save. A real MD item lookup test proves a second SQL connection cannot change the read item until commit; the saved name remains the original snapshot after a later MD change. Other MD references and quotation conversion still need focused concurrent verification.
- BR-SD-017 customer stability checkpoint (2026-10-27T20:28:06+08:00): the real approved MD customer contract read participates in the same Serializable transaction. A second connection's rename times out until the order commits, and the saved order keeps the original customer name after a later rename. Currency and tax contract races remain to verify.
- BR-SD-018: Submit and final approval revalidate customer status and credit through an FI/AR public contract. The contract must return available limit and exposure for the same company/customer/business date; SD never reads FI tables. Until this contract exists, return a named `SAL.CREDIT.UNAVAILABLE` business error and leave order Draft/Pending as appropriate. A future override needs a separate action permission, reason, actor, time and one auditable decision per approval round; it cannot bypass inactive/unapproved customer or company checks. No placeholder exposure or automatic approval is allowed.
- BR-SD-019: Delivery balance is derived from saved order quantity minus posted delivery and active pending reservation. A delivery cannot exceed it. Approved order cancellation requires zero active pending and posted deliveries and a current version; cancellation retains number, quote source, lines and SYS history. A soft-deleted Draft does not release a used quotation source. Rejected revision cannot alter source identity. No order action writes INV; delivery posting is governed by BR-SD-005–007.
- BR-SD-020: Order list/detail queries use action scope before lookup; a 404 hides cross-company/out-of-scope IDs. Each write replaces all draft lines in one transaction and checks decimal overflow, duplicate line IDs, precision, valid references, status and concurrency before commit. No batch/partial success semantics apply. API and UI show specific field, state, credit or conflict reasons; no zero-change success message.

## WU-SD-004d outbound decisions (planned)

- BR-SD-021: Delivery states are `Draft`, `Pending`, `Rejected`, `Posted`. Create is Draft; edit of Rejected replaces all lines and returns Draft while retaining every SYS round. Only Draft submits or soft-deletes; Pending accepts only a SYS decision; Posted is immutable. Every command checks its exact `SAL.DELIVERY.*` permission, current company, SYS action scope and version before revealing or changing a document. The order must still be Approved at submit and final approval. No draft, rejected or deleted delivery contributes to reserved or posted quantity.
- BR-SD-022: Each saved delivery line has one same-company order-line source, immutable order/item identity, positive base-unit quantity to six places and a positive line number. Multiple delivery lines may target one order line; aggregate them before checking. For each order line, `available = ordered - posted - other active Pending`; reject a negative result and quantities above available. At submit lock affected order lines by ascending ID; at final decision use the same lock, exclude the current Pending reservation from `other` and recheck the entire current quantity. Concurrent submissions, order cancellation and decisions must serialize on these locks; the SQL query uses saved SD documents, never INV aggregates or client-supplied balances. Rejection changes Pending to Rejected atomically, removing its reservation exactly once.

The final-decision saved-row projector rejects a missing current delivery and any selected current row that is deleted or outside Pending. The caller must still load all current saved rows from SQL under the ordered locks; this pure guard cannot prove query completeness.

WU-SD-004a2b4 adds a final-decision entry point that derives the current Pending delivery request from those same saved rows and immediately checks it against the projected balance. The caller cannot pass a smaller independent quantity; 1–1000 current lines are required. SQL must still select the complete same-company row set under ascending order-line locks.

WU-SD-004a2b7 requires a separate `COUNT(*)` of all persisted current delivery lines in the same company-scoped transaction. Selected rows must match that count, have unique positive persisted line IDs, the current delivery ID and one expected active status. The guard returns distinct source order-line IDs in ascending order. SQL must prevent concurrent edits between count, selection, ordered locks and balance reload; this pure guard alone cannot establish transaction isolation.

WU-SD-004a1 implements BR-SD-022's decimal aggregation and balance comparison as a pure guard. Its input is a trusted saved-data snapshot only; WU-SD-004a2 remains responsible for the transaction locks, state, company and scope checks, and live SQL totals.

WU-SD-004a2b2 implements the pure saved-row projector for that snapshot. Posted rows consume quantity even if a historical delete flag is present; only active Pending rows reserve quantity, and the current Pending delivery is excluded before its saved request is checked once. Draft, Rejected and deleted Pending rows do not reserve. Missing/duplicate order lines, malformed quantities, a current delivery already Posted and persisted totals beyond the order quantity are rejected. The SQL caller still owns same-company filtering, locks and a consistent read of the complete saved row set.
- BR-SD-023: Warehouse/location and lot/serial selections are copied into saved lines before submission and revalidated by INV at posting. Tracking sums must equal each line quantity; serial entries carry one unit each and must be available at the selected location. No tracking for an untracked item. A revision revalidates all selected references. The SD handler maps saved lines to `SalesOutboundLine` without a cost or commercial price; `SourceId` is the delivery ID and `BusinessDate` is the saved delivery date. INV remains owner of stock, tracking, source replay and negative-stock checks.
- BR-SD-024: SYS final approval calls the SD `IApprovalResultHandler` in its open transaction. The handler reloads the Pending document and saved version, locks/rechecks order balances, calls `PostSalesOutboundAsync`, stores returned movement IDs and marks Posted before commit. A zero-step `SubmitAsync` does not call the handler, so SD performs this exact sequence itself in the submit transaction. If INV rejects, all SYS/SD/INV changes roll back, leaving Pending for a failed final decision or Draft for a failed zero-step submission. SYS rejection updates SD to Rejected without calling INV. A second decision on Posted/Rejected is a conflict; identical INV replay never licenses a second SD approval.
- BR-SD-025: Posted delivery cannot be edited, deleted or directly reversed. Its order, line, tracking, SYS history and INV movement IDs remain traceable. Future returns must use an explicit new INV source contract. Whole-document save/submit/approval is atomic; invalid middle lines and failed callbacks never produce partial success or a success UI message. No batch or file workflow exists for this feature.

WU-SD-004a2b5 applies BR-SD-022 at Draft submission using every selected saved current Draft line and all Posted/other Pending quantities from one transaction snapshot. Missing, deleted, mixed-state or over-1000 current lines are invalid; no independent client quantity can reduce the checked request. The SQL caller still owns complete same-company selection, ordered locks and atomic SYS/INV effects.

WU-SD-004a2b6 prepares BR-SD-022's order-line lock sequence from saved current Draft/Pending rows. It rejects mixed delivery IDs or states, deleted and invalid lines, caps the set at 1000 saved rows, and returns distinct positive order-line IDs in ascending order. SQL must establish complete same-company selection and acquire those locks before rereading all balance rows; this helper does not perform a lock or prove transaction isolation.

## WU-SD-005d pricing decisions (planned)

- BR-SD-026: SD owns price rules; MD supplies approved customer, active item and currency identities through public Contracts. A rule belongs to one company, item and currency, optionally one customer, with inclusive `valid_from`/`valid_to`, a nonnegative six-place unit price and a four-place ordinary discount ceiling between 0 and 100. Active intervals of the same company/item/currency/customer specificity cannot overlap, including concurrent creates or revisions. Customer-specific active rules take precedence over the default rule; there is no arbitrary tie-break. Historical inactive/deleted rules remain identifiable on saved documents. A rule cannot cross companies or silently use a price from another currency.
- BR-SD-027: An automatic quote uses the document business date, not `IClock.Today`, with inclusive validity. Missing active rule returns `SAL.PRICING.RULE_NOT_FOUND`; overlapping candidate rules are an integrity conflict, never a guessed price. A pricing quote is read-only and returns the selected rule ID/version, unit price, ordinary discount ceiling and expiry with an `asOf` date. Its result is advisory: create/edit must resolve and validate the rule again in its transaction, so a stale quote cannot authorise an obsolete price. No rule is needed when a user explicitly enters an authorised manual price.
- BR-SD-028: Ordinary discount is permitted within the selected rule ceiling. Manual unit price, absence of a rule, or discount above that ceiling requires `SAL.PRICING.OVERRIDE` in addition to the document CREATE/EDIT action, a nonblank reason, and audit of actor/time/reason/old rule price and chosen price. A discount over 100 or below 0, negative price, excess decimal places or invalid reference is never overridable. The server ignores any client-supplied override actor, timestamp, rule version or calculated amount. A source quotation converted to an order copies its immutable commercial snapshot and does not require a new pricing override.
- BR-SD-029: On quotation or manual-order save, server selects the applicable pricing rule and checks override authority under the exact action's SYS data scope, then applies BR-SD-014/017 using the effective business-date output tax and exchange rate. Save line snapshots include source rule ID/version, chosen unit price, discount, override decision/reason and rounded original/base net, tax and gross. Header totals sum rounded saved lines. Rule deactivation, deletion, price change, tax/rate change or a later date cannot rewrite any saved quote/order, including Approved documents. A subsequent Draft revision is a new decision that revalidates all lines and records its own audit; converted source lines cannot be repriced.
- BR-SD-030: Rule mutation and document save are whole-transaction operations with optimistic version checks and same-company isolation. Duplicate/overlap, stale rule quote, out-of-scope identity and changed pricing decision produce named conflict or validation errors with no partial saved lines, no false success and no leaked other-company rule. Price quote causes zero data change and therefore never shows a save-success message. No batch pricing or file import exists in this first release.

## WU-SD-006d credit decisions (planned)

- BR-SD-031: FI/AR owns the effective customer credit limit and posted open receivable exposure in the company's base currency. Its public credit snapshot accepts company ID, customer ID and evaluation date from `IClock.Today` at each decision, and returns currency, limit, current open AR, as-of date/version and availability status. A backdated order never selects historic headroom. A missing, disabled or ambiguous limit, unavailable FI/AR service, mismatched currency/company/customer, negative or overflowed figures, and stale snapshot fail closed with named reasons. Zero limit is valid and blocks positive exposure. SD neither queries FI tables nor substitutes an estimated AR amount.
- BR-SD-032: SD derives its own commitment from Approved orders' saved base-currency gross value still uninvoiced into a posted FI receivable. Pending orders do not reserve credit. On Draft submit add the candidate saved gross once; on Pending final decision exclude the candidate order ID from the commitment query before adding it once. Credit headroom equals limit minus open AR minus other SD commitments minus candidate, with checked decimal arithmetic and no client-provided exposure. If invoices post to FI, the matching SD commitment decreases in the same transaction that increases FI AR exposure; an unposted invoice does not release it. Cancelled orders cannot contribute, and returns/credit notes change FI exposure only after posting. Revisions never rewrite another approved order's historical amount.
- BR-SD-033: Every order submit, final SYS approval and zero-step approval acquires a FI-owned credit-key lock for `(company,customer)` in a common SQL transaction, then reads the fresh FI snapshot and SD commitments. FI credit limit/AR changes and SD order approval/invoice transfers use the same lock discipline. Lock ordering is credit key before order row and stable IDs within SD to avoid deadlocks; the migration/real SQL tests must prove concurrent approvals cannot both consume the same headroom. A read-only check is advisory and carries `asOf`/version; it never authorises a later write.
- BR-SD-034: An over-limit result has a specific excess amount. Only `SAL.CREDIT.OVERRIDE` plus the order's exact SUBMIT or SYS PROCESS action permits a reasoned override. The user supplies a nonblank reason, not actor, timestamp, limit or measured exposure. The server binds one override decision to order ID/version and SYS round, saves actor, `IClock` time, reason, snapshot components and excess once in the approval transaction, and rejects replay or stale round/version. A later round or changed exposure requires a fresh decision. Override cannot bypass inactive/unapproved MD customer, missing FI data, mismatched currency, invalid amount or company access.
- BR-SD-035: `SAL.CREDIT.VIEW` provides only current-company, SYS action-scope customer checks and exposes limit, AR, SD commitments, candidate amount, available balance, business date and a human-readable reason; no FI document detail or other-company figures leak. Order CREATE/EDIT/SUBMIT users may see their own order's credit result without a separate CREDIT.VIEW grant. A preview is read-only and displays that approval will recheck. UI must show numerical refusal, unavailable data, override requirement and successful saved decision distinctly in three languages; no success toast for preview or a failed command.
- BR-SD-036: FI/AR contract, SD approval and override history have separate owners. `sal_credit_override` is an append-only SD audit record linked to the order/round; no cross-module FK/navigation. Failed FI lookup, customer validation, SYS callback, audit insert or concurrency check rolls back the entire order decision. Read-only preview and one-order commands have no batch/file partial-success semantics. WU-SD-006d defines this contract only; 006a/b/c must prove it with real SQL, authorised HTTP and UI tests before claiming credit control works.

## WU-SD-007d invoice decisions (planned)

- BR-SD-037: An invoice has one company, customer, order and saved currency. Its lines may reference multiple Posted deliveries of that order, but each line references one immutable delivery line and source order line. Draft, Pending, Rejected and deleted deliveries are ineligible. The customer/order/currency and source line identities must match on every line; no cross-company joins, client-supplied source state or quantity balance are trusted. ISSUE is one atomic command, not a partial batch; it requires `SAL.INVOICE.ISSUE`, current company and SYS action scope. VIEW uses its own `SAL.INVOICE.VIEW` scope. A 404 hides inaccessible source IDs.
- BR-SD-038: For each delivery line, invoiceable base-unit quantity equals its saved Posted quantity minus quantities on all committed Posted invoice lines, including any soft-deleted historical rows. ISSUE locks distinct delivery-line IDs in ascending order and rechecks the aggregate in the transaction; duplicate source rows in one request are combined for this check but retain distinct requested lines only if they have distinct line numbers. Quantity is positive with at most six decimal places. Exact remaining quantity is allowed; one smallest unit above it, two concurrent issuers, or a zero remaining balance fail with named 409/422 and create no number or FI posting.
- BR-SD-039: The invoice uses the saved order-line commercial net/tax/gross, tax identity/rate, currency and exchange-rate snapshots carried through the Posted delivery, never current MD pricing/tax/rate. For each order line, allocate saved original and base net/tax separately across invoiced portions by cumulative quantity: the new cumulative component is `Money.Round(savedComponent * cumulativeInvoicedQuantity / orderedQuantity, currency)` (base components use base currency); the current component is that cumulative amount minus prior invoiced components. The final portion receives the exact saved net/tax remainder, even across deliveries; gross for each portion is allocated net plus tax and must reconcile to the saved gross. Use checked decimal arithmetic and reject inconsistent source snapshots or overflow. This prevents per-partial rounding drift and preserves immutable posted invoices.
- BR-SD-040: SD saves a permanent invoice number, immutable source links, posting status, source request key and monetary/tax snapshots before calling the FI/AR public posting contract in the same SQL transaction. FI owns the receivable/journal and returns a stable posting ID; SD stores only that reference, never writes FI tables. FI enforces uniqueness for `(company, sourceModule=SD, sourceType=Invoice, invoiceId)` across retries and soft deletion. An identical request key with the same canonical payload returns the existing saved invoice without another FI posting or success claim of a new change; the same key with a different payload is 409. A retry after unknown timeout must first query the saved invoice by request key.
- BR-SD-041: Acquire the FI-owned `(company,customer)` credit lock before SD order and delivery-line locks; FI receivable posting and SD commitment release share this transaction and lock. The released SD commitment is the posted invoice's saved base gross allocated to the source Approved order, capped by its remaining uninvoiced commitment. FI open AR increases by that same amount before commit, leaving total credit exposure unchanged at transfer. A failed FI call, mismatched amount/currency, missing credit contract, audit failure or transaction rollback leaves both sides unchanged. Any FI tax/GL posting is FI-owned; the public result must prove receivable amount, currency and source identity match the SD snapshot.
- BR-SD-042: Posted invoices cannot be edited, deleted or directly reversed. Corrections use a separately designed credit note and FI reversal, preserving the original invoice, order, delivery, AR posting and audit trail. Invoice list/detail show saved totals and FI posting reference; no preview or rejected retry is a new-save success. Error responses identify line/source, quantity, tax snapshot, FI availability, conflict or version. WU-SD-007d defines only the contract; 007a/b must prove SQL constraints, authorised HTTP, rollback and visible-versus-persisted UI results.

## WU-SD-008d return decisions (planned)

- BR-SD-043: A return has Draft, Pending, Rejected and Posted states and references Posted delivery lines of one company, customer and order. Draft edit/delete is versioned; Rejected revision returns Draft and retains SYS rounds. Pending accepts only SYS decision. Posted is immutable. CREATE/EDIT/SUBMIT/VIEW/DELETE use distinct `SAL.RETURN.*` permissions and SYS action scopes; inaccessible source IDs return 404. Zero-step SYS submission runs the same final posting path in the submit transaction.
- BR-SD-044: For each delivery line, returnable quantity is saved Posted quantity minus every committed Posted return quantity, including soft-deleted history. A requested return line explicitly partitions positive six-place quantity into invoice-linked billed portions and an unbilled portion; each billed portion references a saved Posted invoice line of that delivery line. Sum of portions equals requested quantity. Under ascending delivery/invoice-line locks, billed returned quantity cannot exceed its invoice-line quantity net of prior Posted returns; unbilled returned quantity cannot exceed delivered quantity minus all Posted invoices and prior unbilled Posted returns. Pending returns reserve no balance, so final approval rechecks. Concurrent invoice issuance and return posting serialize on the same delivery-line lock and see both committed allocations.
- BR-SD-045: Extend INV's public external-posting contract with a new `SALES_RETURN` inbound source, distinct from `SALES_OUTBOUND`. SD passes saved return ID, line IDs, business date, destination warehouse/location, received tracking and original outbound movement IDs/quantities from the Posted delivery. INV validates same-company source and compatible item/base unit/tracking, derives reversal cost from the original outbound movement cost allocation and returns new movement IDs plus cost evidence; SD never sends sales price as cost or writes INV tables. The inbound is physical receipt to the chosen valid warehouse, so its new movement is retained separately from the original outbound. INV enforces `(company,sourceType,sourceId,lineId)` idempotency even after soft deletion; identical replay returns existing movements, changed snapshot conflicts. A damaged or missing outbound reference blocks posting.
- BR-SD-046: FI owns credit-note, tax reversal, AR and GL rows. For billed portions, SD derives original/base net and tax reversal by cumulative quantity against the immutable invoice-line amount, with final remainder exact; FI's public `PostSalesReturnCreditAsync` accepts saved return source and invoice/FI posting references and returns credit-note ID, company, currency and amount for verification. A return across multiple invoices produces one FI credit source with a breakdown by original invoice; it never edits those invoices or their posted journals. Credit cannot exceed the uncredited original invoice components. FI source uniqueness prevents a second credit after retry or soft deletion.
- BR-SD-047: For unbilled portions, SD reduces only the matching Approved order's uninvoiced commitment by the saved commercial gross allocation, using cumulative quantity and exact final remainder without changing saved order or delivery totals. It must account for all prior invoice and return allocations to avoid duplicate release. Acquire FI `(company,customer)` credit lock first, then SD order, delivery-line and invoice-line IDs in stable order. FI credit posting, SD commitment release, INV inbound, SYS final decision, return status and audit save share one SQL transaction. A billed credit reduces FI open AR; an unbilled return reduces SD commitment. Failed FI/INV/mismatched result rolls back both, with no partial success or inventory-only return.

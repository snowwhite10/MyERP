The backend separates the API composition root, shared core, shared infrastructure, one migrations assembly, and module implementation and Contracts projects. Within a module, the API layer defines HTTP endpoints and DTOs; the application layer coordinates use cases, validation and authorization; the domain layer owns business rules; infrastructure implements persistence and external access. Dependencies point inward, and Contracts provide the published surface for synchronous cross-module calls and integration events. Architecture tests check module references, domain isolation and selected unsafe API use.

One scoped EF Core database context and a single migration sequence support atomic changes across cooperating modules without permitting direct cross-module table access. Cross-module references store identifiers without EF navigation or database foreign keys. Common services provide the clock, decimal money rules, company context, filters, audit and version handling, pagination, and error responses. Ordinary transactions use EF Core; complex batch calculations and reports may use versioned stored procedures. Accounting postings must pass through the finance contract when that implementation becomes available, and modules must not alter posted vouchers or stock summaries directly.

The Angular application uses shared routing, authorization, translation, theme and error-handling facilities. Module pages and their tests are added as work units reach implementation. This structure makes ownership and test boundaries explicit, but it does not mean that all modules in the target architecture are complete. Unit and architecture tests check isolated rules and dependencies; SQL integration, browser and real startup-path tests establish behavior across processes when the required services are available. The progress report identifies the current implementation and verification status.

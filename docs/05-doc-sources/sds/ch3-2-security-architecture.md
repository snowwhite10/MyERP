Security starts at the HTTP boundary. Configured known proxies control whether forwarded client headers are accepted. The API adds security headers, applies transport security outside Development, restricts cross-origin requests to configured origins, authenticates JWT access tokens, and applies request limits before company and permission checks. The frontend has its own Content Security Policy and security-header requirements. Proxy, origin, certificate and frontend hosting settings must be checked in the target deployment.

System authentication uses password hashing, a login captcha, account lockout, short-lived access tokens and rotating refresh tokens backed by Redis-compatible storage. Logout revokes the refresh token. The Development-only captcha master code is rejected outside Development. Protected operations check company access, declared permission codes, IP allowlists where configured, and the user's data scope on the server. Client-side action visibility is a usability aid; it does not grant access. Invalid input, authorization failures and version conflicts return structured ProblemDetails with stable error codes.

Company and soft-delete query filters, audit stamping and optimistic concurrency protect business records within the shared persistence layer. Structured logs include trace, user, company and module context; audit records capture relevant changes. Secrets belong in environment configuration or user secrets rather than source control. Dependency review and vulnerability checks are part of the maintenance process. These controls describe the implemented framework and its intended use by modules; each unfinished module still needs its own permission, data-scope and audit acceptance evidence, and security of a production installation requires deployment verification.

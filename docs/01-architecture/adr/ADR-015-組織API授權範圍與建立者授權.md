# ADR-015：組織 API 的授權範圍與公司建立者授權

- 日期：2026-10-10
- 狀態：採用
- 工作單元：WU-SYS-001

## 背景

WU-SYS-004 完成 `[RequirePermission]` 與公司存取中介層（ADR-014）後，公司／分店／部門的內部服務可以開放為 API。有三個問題規格沒有寫明：

1. 公司本身是隔離根，沒有 `company_id`，Global Query Filter 不適用。持有 `SYS.COMPANY.EDIT` 的用戶，能否修改自己沒有授權的公司？
2. 新建的公司沒有任何用戶關聯。建立者切換不到新公司，就無法維護它的分店與部門；而用戶權限頁要到 WU-SYS-015 才會做。
3. 停用公司後，`UserAuthorizationStore.ListCompaniesAsync` 不再列出這間公司（ADR-014 規定停用公司不可存取）。若公司列表也只列啟用公司，就沒有地方可以把它重新啟用。

## 決定

1. **公司 API 只涵蓋「用戶獲授權的公司」。** 範圍取自 `UserAuthorizationStore.ListManagedCompanyIdsAsync`：用戶與用戶公司關聯都要啟用，公司本身可以是停用狀態，已軟刪除的公司由查詢篩選排除。列表只列出這些公司。修改的目標公司不在範圍內時回 **404 `SYS.COMPANY.NOT_FOUND`**，不回 403，避免透露其他公司是否存在。權限仍按 `X-Company-Id` 的公司判斷（例如在 A 公司有 `SYS.COMPANY.EDIT`，就可以修改自己也獲授權的 B 公司）。原因是公司維護屬於集團層級的管理動作；若要求在 B 公司本身另有權限，停用的 B 公司就永遠無法重新啟用。
2. **列表預設只列啟用公司**，`includeInactive=true` 時才一併列出已停用公司，供重新啟用。分店與部門列表則一律包含已停用資料，以狀態標籤區分；它們本來就限於目前公司，不需要另設開關。
3. **建立公司時，在同一交易內授權建立者。** 系統新增一筆建立者對新公司的 `sys_user_company`（非預設、啟用），並複製建立者在目前公司（`X-Company-Id`）的角色。整個過程使用同一個 DbContext 交易，不會出現「公司已建立，但建立者沒有存取權」的半完成狀態。其他用戶對新公司的存取，透過 `PUT /users/{id}/companies/{companyId}` 指派。
4. 分店與部門沿用 Global Query Filter 與 `CompanyAccessMiddleware`。其他公司的資料一律回 404；以其他公司的分店或上級部門作為參照時，回 400。

## 後果

- 正面：公司資料不會越權修改；停用的公司可以重新啟用；建立公司後可以馬上切換過去，接着維護分店與部門。
- 負面：建立者會繼承目前公司的全部角色，權限可能比需要的大。之後可在用戶權限頁（WU-SYS-015）調整，稽核日誌（WU-SYS-007）會記錄這筆授權。
- 前端：公司頁提供「顯示已停用」勾選。新建公司要等下次載入授權（重新整理或重新登入）才會出現在頂列的公司清單；`PermissionService.load()` 在切換公司時也會重新載入。

# ADR-064：PUR／SD 與 INV 的過帳邊界

- 日期：2026-10-14
- 狀態：Accepted
- 工作單元：WU-INV-015d

## 情境

PUR 與 SD 尚未建立。INV 已提供 `IInventoryPostingService`，可按目前公司、來源類型與來源 ID 防重放，並在呼叫方交易中追加異動；但它不認識採購入庫或銷售出庫單據，也不能自行證明來源已核准。BlueWhale 將兩種核准介面列在 Inventory 5.19／5.8；MyERP 的業務單據仍應由 PUR／SD 擁有。

## 決策

1. INV 保持唯一異動寫入者。PUR 入庫與 SD 出庫只引用 `MyERP.Modules.Inventory.Contracts` 的 Application 契約，不讀寫 `inv_` 表，也不在兩個模組中複製 INV 異動資料或庫存結存。
2. PUR 使用固定來源 `PURCHASE_INBOUND`、方向 `In`；SD 使用固定來源 `SALES_OUTBOUND`、方向 `Out`。來源 ID 為各自已保存單據的 ID，於同一公司內與來源類型組合唯一。來源行號、基本單位六位數量、物料、倉庫、儲位和批序號由已保存明細映射；PUR 的入庫單價是單據保存的成本快照，SD 出庫成本必為 null。若有單位換算，由來源模組在保存單據時完成並保存轉換結果，不把單據顯示單位傳給 INV。
3. SYS 工作流最終核准回呼進入來源模組處理器。處理器重新讀取**目前公司、待審狀態、版本與已保存明細**，在同一 `MyErpDbContext` 交易中呼叫 INV 過帳，再將來源狀態改為 Posted，最後才提交；INV 不接受由 HTTP 用戶端直接提供的「已核准」宣稱。駁回只改來源狀態，不過帳。任何 INV／MD／SQL 失敗都回滾 SYS 決定、來源狀態、引用及異動。來源模組對已 Posted 單據禁止修改、刪除與再次核准。
4. INV 既有來源鎖與 `(company_id, source_type, source_id, source_line_no, direction)` 唯一約束作第二道防線；相同日期和完整明細重送回原異動 ID、`Replayed=true`，任一差異回 409 `INV.POSTING.CONFLICT`。呼叫端在重試前仍須檢查來源狀態，不得把重放結果解讀為再次核准成功。反向沖回用新的來源單據及 ID，不更改已過帳異動。
5. INV 契約不新增公開寫入 API 或 PUR／SD 專用權限。權限和審批由來源模組的 HTTP／Application 層執行。BlueWhale 的 INV 5.8／5.19 核准介面保留在對照表，實際操作入口由 SD／PUR 單據頁或 SYS 待審任務提供，避免第二份可核准的 INV 單據。
6. 分批交付：015d 固定邊界與驗收；015a 在 INV Contracts 定義來源型別及受限呼叫契約，先寫真實 SQL 測試驗證公司隔離、方向、來源重放、同交易回滾和批序號；015b 在來源模組建立時各自實作 SYS 回呼與真實 HTTP／SQL 跨模組測試。015a 完成即可結束 INV 側工作；015b 依賴實際 PUR／SD 單據，不能以測試假單據代替。父 WU-INV-015 要在 015a、015b 都完成後結案。

## 後果

現有通用 `IInventoryPostingService` 保留給 INV 自有單據；015a 要檢查專用契約是否能收窄來源型別與方向，同時避免建立新的繞過審批入口。來源模組成立前，真實跨模組 HTTP 驗收只能列為待完成；測試替身只能驗證 INV 契約本身。INV 模組收尾如需早於 PUR／SD 完成，須在 backlog 明確記錄 015b 的依賴與尚未驗收範圍，不可把它標為通過。

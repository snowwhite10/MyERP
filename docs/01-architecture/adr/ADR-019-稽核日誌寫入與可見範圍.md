# ADR-019：稽核日誌的寫入方式、交易與可見範圍

- 日期：2026-10-11
- 狀態：採用
- 工作單元：WU-SYS-007

## 背景

MASTER_PROMPT 第 8.2 節要求所有業務變更寫入 `sys_audit_log`：時間、用戶、公司、表名、記錄 Id、操作類型、欄位舊值與新值、來源 IP、TraceId，而且只能新增，不能修改。登入、登出、萬用碼登入與權限變更也要留下記錄（REQ_F4118.24.4）。稽核必須和業務資料一起提交或一起回滾。

## 決定

1. **寫入點**：`AuditTrailInterceptor`（Shared.Infrastructure）排在 `AuditSaveChangesInterceptor` 之後，所以稽核看到的是已蓋章的值。
   - 修改與刪除在 SaveChanges 之前產生記錄。
   - 新增要等資料庫產生 Id，所以在 SavedChanges 再呼叫一次 SaveChanges 寫入。
   - 有稽核記錄而呼叫端沒有開交易時，interceptor 自己開交易，業務資料和稽核一起提交。原因是 EF 對單一批次不開交易：沒有交易時，業務 UPDATE 因版本衝突失敗，稽核 INSERT 仍可能已被提交。
2. **失敗清理**：SaveChanges 失敗時，interceptor 取消本次加入的稽核實體，並回滾自己開的交易，所以呼叫端重試時不會寫出重複記錄。樂觀鎖衝突時 EF 不呼叫 `SaveChangesFailed`，只呼叫 `ThrowingConcurrencyException`，所以兩個掛鉤都要處理。
3. **欄位差異**：以 snake_case 欄位名寫成 `{"欄位":{"old":…,"new":…}}`。
   - 修改只列出值真的有變的欄位；沒有任何變更時不寫記錄。
   - 不記錄的欄位：主鍵、審計欄位、`version`、`company_id`。
   - 標記 `[SensitiveData]` 的欄位（例如 `password_hash`）只記錄「有變更」，值以 `***` 遮蔽。
   - 標記 `[NotAudited]` 的實體不記錄，例如稽核表本身。
   - 軟刪除（`is_deleted` 由 false 變 true）記為 DELETE。審批、作廢、過帳由 Application 層以 `IAuditTrail.MarkAction` 指定操作類型。
   - 不經 ChangeTracker 的 `ExecuteUpdate`／`ExecuteDelete` 不會被記錄。凡是業務變更都不得使用它們；現有的例外有兩個，都已有安全事件涵蓋：登入時用 `ExecuteUpdate` 原子更新失敗計數、鎖定與重新雜湊，由 LOGIN／LOGIN_FAILED 涵蓋；用戶公司授權取消舊的預設公司，由 PERMISSION_CHANGE（含 `isDefault`）涵蓋。
4. **安全事件**：以 `IAuditTrail.AddSecurityEvent` 暫存，在下一次 SaveChanges 時與其他變更同一交易寫入。
   - 登入相關事件由 AuthService 立即儲存：LOGIN、LOGIN_FAILED（原因只寫 `INVALID_CREDENTIALS` 或 `PASSWORD_EXPIRED`）、LOGOUT、MASTER_CODE_LOGIN。萬用碼登入不論帳密是否正確都記錄。
   - 權限變更（PERMISSION_CHANGE）與角色或授權的變更同交易寫入，記錄操作者以及新增和移除的權限。
   - 事件明細不得包含密碼、Token 或 Captcha 答案。
5. **只增不改**：資料庫以 `INSTEAD OF UPDATE, DELETE` trigger 拋出 `sys_audit_log is append-only`；`changes` 欄位有 ISJSON 約束。
6. **公司歸屬與可見範圍**：
   - 公司擁有的資料記為該公司。全系統表（例如 `sys_user`、`sys_role`）的變更記為操作時的公司；未登入請求的公司標頭未經驗證，不採用。
   - 查詢 API（`SYS.AUDIT.VIEW`）只列出兩類記錄：屬於目前公司的記錄；沒有公司、但用戶屬於目前公司的安全事件（例如登入）。
   - 帳號不存在的登入失敗沒有用戶，只留在資料庫與應用程式日誌，任何公司都看不到，以免洩露其他公司的帳號嘗試。
7. **交易內的 Warning**：連線字串啟用 MARS 時，EF 對交易內的每次 SaveChanges 都寫 `SavepointsDisabledBecauseOfMARS` Warning。稽核交易令這種情況成為常態，因此忽略這個事件。

## 後果

- 每次有新增的 SaveChanges 多一次資料庫往返（寫入 CREATE 稽核）；可接受。
- 業務代碼不得以 `ExecuteUpdate`／`ExecuteDelete` 或原生 SQL 修改業務資料，否則會漏掉稽核（第 18 節已禁止直接 UPDATE 庫存彙總等）。
- 稽核表會持續增長；歸檔與分區策略留待 BI 或維運階段另立 ADR。

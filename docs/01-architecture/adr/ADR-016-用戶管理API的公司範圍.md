# ADR-016：用戶管理 API 的公司範圍

- 日期：2026-10-11
- 狀態：採用
- 工作單元：WU-SYS-002

## 背景

`sys_user` 是全系統的登入身分，本身沒有 `company_id`，Global Query Filter 不適用。用戶與公司的關係只記錄在 `sys_user_company`。開放 `/api/v1/sys/users` 時，有三個問題規格沒有寫明：

1. 持有 `SYS.USER.*` 權限的用戶，可以看到及修改哪些用戶？
2. 新建的用戶沒有任何公司關聯。如果列表只列有關聯的用戶，新用戶會在建立後立即「消失」。
3. 重設密碼的風險比啟用／停用高，是否沿用 `SYS.USER.EDIT`？

## 決定

1. **範圍是 `X-Company-Id` 指定的公司。** 列表、修改、重設密碼、解鎖都只涵蓋在該公司有 `sys_user_company` 關聯的用戶（關聯或用戶本身停用也算，以便重新啟用）。範圍外的用戶一律回 **404 `SYS.USER.NOT_FOUND`**，不回 403，避免透露其他公司的帳號是否存在（比照 ADR-015）。
2. **建立用戶時，同一交易內加入目前公司。** 系統新增一筆啟用、設為預設公司、沒有角色的 `sys_user_company`。新用戶能登入，但在授予角色前沒有任何權限；角色由 `PUT /users/{id}/companies/{companyId}`（之後由 WU-SYS-015 用戶權限頁）指派。
3. **帳號全系統唯一。** 帳號如已在其他公司存在，仍回 409 `SYS.USER.DUPLICATE`，不會靜默把既有用戶加入本公司（否則等於讓任何公司管理員接管他公司的帳號）。把既有用戶加入另一間公司，必須由同時管理兩間公司的人透過公司授權指派。
4. **重設密碼另設權限 `SYS.USER.RESET_PASSWORD`。** 啟用／停用與解鎖用 `SYS.USER.EDIT`。全權角色自動擁有新權限。
5. **不可停用自己**（422 `SYS.USER.SELF_DEACTIVATION`），避免唯一的管理員把自己鎖在系統外。
6. 帳號建立後不可修改。DTO 只回 `isLocked`、`isPasswordExpired` 兩個布林值，不回雜湊、失敗次數或鎖定期限。

## 後果

- 正面：公司管理員只能管理自己公司的用戶；新用戶建立後立即出現在列表；高風險的重設密碼可以單獨授權。
- 負面：多公司用戶可以被任何一間所屬公司的管理員停用或重設密碼，影響範圍是全系統。這符合「單一登入身分」的設計，稽核日誌（WU-SYS-007）會記錄操作者。
- 待辦：重設密碼目前不撤銷該用戶既有的 Refresh Token（Redis 沒有按用戶的索引）；停用則已由刷新時的「用戶須啟用」檢查擋下。按用戶撤銷 Token 留給 WU-SYS-007／安全強化工作單元處理。`PUT /users/{id}/companies/{companyId}` 尚未限制目標公司必須是操作者獲授權的公司，WU-SYS-015 須補上。

# ADR-017：用戶公司授權指派的範圍

- 日期：2026-10-11
- 狀態：採用
- 工作單元：WU-SYS-015

## 背景

WU-SYS-004 開放了 `PUT /api/v1/sys/users/{userId}/companies/{companyId}`，只要求 `SYS.USER.EDIT`。這個權限是在 `X-Company-Id` 指定的公司內檢查的，但端點沒有限制目標用戶和目標公司。結果，公司 A 的管理員可以做到：

- 把任何帳號（包括只屬於公司 B 的帳號）加入公司 A，等於接管他公司的帳號。這違反 ADR-016 第 3 點。
- 在自己沒有獲授權的公司 B 替用戶授予全權角色。

ADR-016 已把這個問題列為 WU-SYS-015 的待辦。用戶權限頁還需要讀取用戶現有的授權，原本沒有查詢端點。

## 決定

1. **目標用戶必須屬於目前公司。** 用戶在 `X-Company-Id` 公司要有 `sys_user_company` 關聯（停用的也算，這樣才能重新啟用），否則回 **404 `SYS.USER.NOT_FOUND`**。範圍與用戶管理 API 相同。
2. **目標公司必須是操作者獲授權的公司**，即 `UserAuthorizationStore.ListCompaniesAsync(operator)`：公司、關聯、用戶都啟用。否則回 **404 `SYS.COMPANY.NOT_FOUND`**（比照 ADR-015，不透露公司是否存在）。要把用戶加入另一間公司，操作者必須同時管理兩間公司。
3. **不可停用自己的公司授權**，回 422 `SYS.USER.SELF_DEACTIVATION`。原因與 ADR-016 第 5 點相同：避免唯一的管理員把自己鎖在系統外。移除自己角色的情況沒有阻擋，可以由其他管理員恢復，稽核留給 WU-SYS-007。
4. **新增 `GET /api/v1/sys/users/{userId}/companies`**（`SYS.USER.VIEW`）。用戶範圍與第 1 點相同，只回傳操作者獲授權公司的指派：`companyId`、公司代碼與名稱、`branchId`、`departmentId`、`isDefault`、`isActive`、`roleIds`，依公司代碼排序。操作者無權管理的公司不列出，避免透露用戶在其他公司的設定。
5. 內部的 `RoleService.AssignAsync` 保留給種子資料與測試使用，不做範圍檢查。API 一律經過 `AssignInScopeAsync`。

## 後果

- 正面：公司管理員只能在自己管理的公司內授權，帳號接管和越權授予全權角色都被阻擋。
- 負面：管理員看不到用戶在其他公司的授權。這是刻意的取捨，因為前端只能編輯可管理的公司。
- 前端：用戶權限對話框的公司下拉只列出操作者可切換的公司。選擇其他公司的分店／部門時，以該公司的 `X-Company-Id` 查詢；操作者獲授權於該公司，所以公司存取中介層會放行。

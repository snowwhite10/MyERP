# ADR-018：安全中介層、限流分區與 Token 存放

- 日期：2026-10-11
- 狀態：採用
- 工作單元：WU-SYS-005

## 背景

MASTER_PROMPT 第 7 節要求 HTTPS/HSTS、CORS 白名單、Rate limiting（登入類每 IP 每分鐘 5 次、一般 API 每用戶 300 次、匯出每用戶 10 次）、安全標頭與只信任設定 Proxy 的 ForwardedHeaders。ADR-013 把「CSP 實施時是否改用 HttpOnly Cookie 存 Token」留到本工作單元評估。

## 決定

1. **限流分區**
   - login、refresh：每 IP **每端點** 5 次／分鐘。合併計數會令一次正常登入（captcha + login）就用掉兩次。
   - captcha：每 IP 10 次／分鐘。每次登入失敗前端會換新題，5 次登入嘗試至少需要 6 題；Captcha 本身不驗證帳密，放寬不影響防暴力破解。
   - 已登入請求：每用戶 300 次／分鐘（全域限流）；匿名請求只受端點政策限制，並以 ArchitectureTests 強制每個匿名端點都有按 IP 的政策。
   - 匯出：先定義 `RateLimitPolicies.Export`（每用戶 10 次），匯出端點出現時套用。
   - 固定視窗、不排隊。限流狀態存在程序記憶體；目前只有一台 API 主機。改為多台時改用 Redis 分散式限流（新 ADR）。
2. **429 回應**：限流只設狀態碼與 `Retry-After`，由既有 StatusCodePages 產生 ProblemDetails；`FromStatus(429)` 補上 `COMMON.REQUEST.RATE_LIMITED`。前端用共用的 `apiErrorKey` 把 429 一律顯示為三語「操作過於頻繁」。
3. **ForwardedHeaders**：沒有設定任何 Proxy 時不註冊中介層，因為框架在兩個清單皆空時信任所有來源。
4. **HTTPS/HSTS**：只在非 Development 啟用；HSTS 一年、含子網域。
5. **CSP**：API 回應用 `default-src 'none'; frame-ancestors 'none'`。前端站台的 CSP 寫在 security.md，並套用到 E2E 靜態伺服器，讓 E2E 驗證前端在此 CSP 下可運作。因 `script-src 'self'` 不允許內嵌腳本，production 建置關閉 critical CSS 內嵌（Angular 的內嵌腳本會被擋）。`style-src` 保留 `'unsafe-inline'`，因為 ng-zorro 會在執行期插入樣式。
6. **Token 存放維持現狀（不改 HttpOnly Cookie）**：Access Token 仍經 `Authorization: Bearer` 傳送，Session 仍存 `localStorage`（ADR-013）。理由：
   - 改用 Cookie 需要 CSRF Token、SameSite 設定；前端與 API 不同源時還要 `AllowCredentials` 與第三方 Cookie 限制，複雜度與風險都提高。
   - 現在 XSS 的主要防線已到位：嚴格 CSP（無內嵌腳本、無外部腳本來源）、Angular 預設跳脫、Access Token 只有 15 分鐘、Refresh Token 一次即輪替。
   - CORS 不允許 Credentials，瀏覽器不會自動附帶憑證，因此不存在 CSRF 面。
   - 日後如要求更高（例如外部稽核要求），再以 BFF 或 HttpOnly Refresh Cookie 方案另立 ADR。

## 後果

- 部署時必須讓前端站台送出 security.md 第 5 節的標頭，並依實際架構設定 CORS 來源與 Proxy。
- 整合測試主機在 `TestDatabase.UseTestDatabase` 放寬登入類限流（TestServer 沒有連線 IP）；限流行為由 `WebSecurityTests` 以預設值驗證。
- 前端首屏不再內嵌 critical CSS，首次繪製可能稍慢（樣式表本身仍經壓縮與快取）。

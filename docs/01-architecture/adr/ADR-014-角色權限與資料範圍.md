# ADR-014：角色、權限代碼與資料範圍的實作

- 日期：2026-10-10
- 狀態：採用
- 工作單元：WU-SYS-004

## 背景

MASTER_PROMPT 第 7 節要求 RBAC，權限代碼格式為 `模組.資源.動作`，另有資料範圍（全公司／分店／部門／本人），且前後端都要檢查，以後端為準。`sys_user` 是全系統身分（WU-SYS-002），公司是隔離根（WU-SYS-001）。客戶端送來的 `X-Company-Id` 原本只做格式解析，還沒有驗證用戶能否存取該公司。

## 決定

1. **權限目錄放在程式碼，不另建 `sys_permission` 表。** 每個模組以 `IPermissionDefinitionProvider` 宣告本模組的代碼。`PermissionCatalog` 在啟動時檢查格式、前綴屬於該模組（例如 SD 用 `SAL.`，FI 可用 `GL.`／`AR.`…）與重複。`sys_role_permission` 只存代碼字串。理由：權限與實作同版本，不必寫同步程序，也不會有資料庫與程式不一致的問題。角色只能授予目錄內的代碼。代碼從目錄移除後，資料庫殘留的授權會被忽略。api-conventions 第 6 節的「由 SYS 種子程序登錄」改為「由模組宣告、SYS 彙整」。
2. **角色為全系統定義，授權按公司。** `sys_role` 沒有 company_id。`sys_user_company` 決定用戶可存取哪些公司，以及在各公司的分店／部門歸屬（每位用戶最多一間預設公司，以篩選唯一索引保護）。`sys_user_role(user_id, company_id, role_id)` 以複合外鍵指向 `sys_user_company`，所以沒有公司存取權就不能指派角色。同一個角色可在不同公司指派給不同用戶。
3. **資料範圍設在角色。** 角色的 `data_scope` 套用到該角色授予的全部權限。同一權限由多個角色授予時，取最寬的範圍（Self < Department < Branch < Company）。`is_full_access` 角色（admin）不必逐一列出權限，任何權限都是全公司範圍。用戶設為分店／部門範圍，卻沒有分店／部門歸屬時，退回「本人」（封閉失敗），避免把「分店為 null 的資料」當成可見範圍。部門範圍目前只含同一部門，不含下級部門；需要時另開工作單元。
4. **後端檢查方式**：
   - `[RequirePermission("SYS.ROLE.VIEW")]`（繼承 `AuthorizeAttribute`，政策名稱為 `perm:{code}`），由 `PermissionPolicyProvider` 動態建立政策，`PermissionAuthorizationHandler` 檢查目前用戶在 `X-Company-Id` 公司是否有此代碼。沒有公司上下文就沒有權限。
   - `CompanyAccessMiddleware` 放在 `UseAuthentication` 之後：已登入的請求若帶 `X-Company-Id`，該公司必須可存取（用戶、公司、關聯都啟用），否則回 403 `COMMON.COMPANY.ACCESS_DENIED`。這樣偽造標頭不能繞過 Global Query Filter，即使端點只需登入也一樣。
   - 授權失敗回 403 ProblemDetails `COMMON.PERMISSION.DENIED`（`ErpAuthorizationResultHandler`）；未登入仍回 401。
   - `ICurrentAuthorization` 在同一請求內只查一次資料庫，Application 層用 `FilterFor(code)` 取得 `DataScopeFilter`，套用到實作 `IDataScopedEntity` 的查詢上。
   - ArchitectureTests 檢查：每個 Controller 動作都要有 `[RequirePermission]`；只有登入、Captcha、刷新可以 `[AllowAnonymous]`；自助端點（`/me`、登出、`/auth/authorization`）列入白名單，只需登入。代碼必須在權限目錄內。
5. **暫不做跨請求快取。** 每個需授權的請求最多查詢 3 次（關聯、角色、角色權限）。權限變更要即時生效，也不必處理快取失效。日後如果日誌分析發現權限查詢成為熱點，再加 Redis 快取，並在角色或授權變更時失效。
6. **前端**：`PermissionService` 進入主框架前（`authorizationGuard`）呼叫 `GET /api/v1/sys/auth/authorization`，同時取得可存取公司與目前公司的權限。本機記住的公司已不可存取（403 `COMMON.COMPANY.ACCESS_DENIED`）時，清除選擇並改用預設公司。切換公司後重新載入。`*erpHasPermission` 與 `permissionGuard(...)` 只控制顯示，後端仍為準。權限載入失敗時以空權限繼續，只顯示不需權限的項目。E2E 以 fixture 模擬此 API（同 ADR-013）。

## 後果

- 新模組必須同時提供 `IPermissionDefinitionProvider`，並為每個 action 標上權限，否則 ArchitectureTests 失敗。
- 單據表需要資料範圍時，須有 `branch_id`、`department_id` 及負責人欄位並實作 `IDataScopedEntity`。
- 組織 API（WU-SYS-001）與用戶管理 API（WU-SYS-002）現在可以依 `SYS.COMPANY.*`、`SYS.USER.*` 開放。
